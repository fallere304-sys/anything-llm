# Tachikoma 設計書 — 好奇心駆動・常駐型ローカルAI

> 対象: Gemma 4 E2B / Ollama / i7-7700 + RAM 16GB + GTX 1060 6GB / Windows 10
> ラベル規約: **[観測事実]** 確認済み / **[合理的推定]** 根拠ある推論 / **[低確度仮説]** 未検証

---

## 0. 問題定義

### 0.1 なぜ Ollama / LM Studio では「タチコマ」にならないのか

[観測事実] Ollama と LM Studio は **要求→応答型の推論サーバー** で、呼ばれない限り何もしない。
状態 (会話履歴以外の世界モデル) も、自発的な行動の選択機構も持たない。

タチコマ的なAIに必要なのは、推論サーバーの *上* に載る次の 4 つである:

| 必要な性質 | 推論サーバーにあるか | 本設計での担当 |
|---|---|---|
| 常に観測している | ない | 感覚器層 (`sensors.py`) |
| 自分が何を知らないかを知っている | ない | 信念ストア (`memory.py`) |
| 知らないことを自分から調べに行く | ない | 好奇心スケジューラ (`curiosity.py`, `probes.py`) |
| 話しかけるタイミングを選ぶ | ない | 発話ポリシー (`agent.py: maybe_speak`) |

**結論: LLM は「脳」ではなく「脳の中の一部品 (言語野)」として扱う。**
思考の持続性・自発性は、LLM の外側にある明示的な状態と制御ループで作る。

### 0.2 好奇心の操作的定義

依頼の仮定をそのまま形式化する:

> 好奇心 = 目の前の状況についての低確度推定をなくすための情報収集行為

これを 3 つの量に分解する。

```
uncertainty(b) = relevance(b) × H(p(b)) × learnability(b)
                 └ 目の前性 ┘  └ 低確度 ┘  └ 調べれば減るか ┘

H(p) = −p·log₂p − (1−p)·log₂(1−p)        # 二値エントロピー: p=0.5 で最大 1

curiosity_drive = max_b uncertainty(b)
probe_value(b, k) = H(p(b)) × reliability(k) × relevance(b) / cost(k)
```

- **H(p)**: 「低確度推定」の度合い。p=0.5 (半々) が最も気になる。
- **relevance**: 「目の前の状況」への近さ。新しい出来事に関係すると上がり、時間で半減 (既定 30 分)。
- **learnability**: 調べるたびに割り引き、`max_probe_attempts` 回で打ち切る (後述の noisy-TV 対策)。
- **probe_value**: 期待情報利得 ÷ コスト。「ユーザーに聞く」は確実だが割り込みコストが高い。

| 案 | 概要 | 評価 |

## 2. アーキテクチャ

```
 ┌──────────────── 感覚器 (CPU・毎tick・LLMなし) ─────────────────┐
 │ ファイル保存差分  端末ログ追記  前面ウィンドウ名  クリップボード  チャット │
 └───────────────┬──────────────────────────────────────┘
                 │ event(source, kind, content)
                 ▼
        ┌─────────────────┐   novelty = 1 − max jaccard(直近の同種イベント)
        │ 知覚 / 新規性判定 │── 低い → 既視感として捨てる (LLM を呼ばない)
        └────────┬────────┘
                 │ 高い
                 ▼
        ┌─────────────────┐   LLM: 状況要約 + 命題(≤4) + 根拠の種類
        │ 評価 (appraisal) │   observed / inferred / guessed
        └────────┬────────┘   → 確率はコードが割当 (0.95 / 0.65 / 0.5)
                 ▼
 ┌────────────────────────────────────────────┐
 │ 信念ストア (SQLite)                                    │
 │  statement | p | 出所 | relevance | half_life | attempts │
 │  ラベル = f(p_now, 出所)  ← LLM に自己申告させない       │
 └────────┬───────────────────────────────────┘
          │ max uncertainty > 閾値 かつ GPU に余裕
          ▼
 ┌──────────────────┐  ┌─────────────────────────┐
 │ 好奇心スケジューラ │→│ プローブ (読み取り専用)          │
 │ 対象の仮説を1つ選ぶ │  │ search_memory / grep_workspace │
 │ LLM: 調べ方と query │  │ read_file / wait / ask_user   │
 └──────────────────┘  └───────────┬─────────────┘
                                     ▼
                    ┌─────────────────────────┐
                    │ 判定 LLM: supports / partial │ → 対数オッズ更新
                    │ / contradicts / irrelevant  │   Δ = w(verdict) × reliability
                    └───────────┬─────────────┘
                                ▼
          ┌────────────────────────────────┐
          │ 発話ポリシー: value ≥ 閾値 のときだけ話す     │
          │ タイピング中は閾値 0.9 (緊急のみ)           │
          └────────────────────────────────┘
          長時間無操作 → 睡眠: 古い出来事の要約・不要な信念の剪定
```

### 2.1 時間スケール (タチコマの「思考の層」)

| 層 | 周期 | 計算資源 | 役割 |
|---|---|---|---|
| 反射 | 2 秒 tick | CPU のみ | 感覚器のポーリング、差分、新規性、関連度の減衰 |
| 評価 | 出来事ごと | GPU 1 回 | 新しい出来事 → 状況の命題化 |
| 好奇心 | 余裕があるとき | GPU 1〜2 回 | 最も不確かな仮説を 1 つ調べて更新 |
| 対話 | ユーザー発言時 | GPU 即時 (最優先) | 把握している状況をラベル付きで答える |
| 睡眠 | 30 分無操作 | GPU 1 回 | 要約 (digest) 作成、反証済み・無関係な信念の削除 |
| 学習 | 2 時間無操作 かつ 新標本 20 件以上 | GPU 占有 (数十分〜) | 裏付けのある標本で LoRA 学習 → 検証 → 採用/棄却 (§10) |

**1 tick あたり背景推論は最大 1 回**、かつ直近 60 秒の GPU 占有率を `gpu_duty_cycle` (既定 50%) 以下に保つ (`GpuGate`)。
ユーザーとの対話はゲートの割合制限を受けない。

## 3. 信念モデル — 「低確度推定」をデータ構造にする

### 3.1 ラベルはコードが決める

```
p_now = 0.5 + (p − 0.5) × 0.5^(経過時間 / half_life)     # 状況は古くなる

[反証済み]   p_now ≤ 0.10
[観測事実]   p_now ≥ 0.90 かつ 出所 ∈ {observation, user}
[合理的推定] p_now ≥ 0.70
[低確度仮説] それ以外
```

### 3.2 出所による確信の上限 (ハルシネーション洗浄の防止)

| 出所 | 上限 p | 意味 |
|---|---|---|
| observation | 0.99 | ファイル・ログなど直接観測 |
| user | 0.99 | ユーザーの明示回答 |
| memory | 0.85 | 過去の記憶からの想起 |
| reflection | 0.75 | LLM の推論のみ |

**LLM が何度「そう思う」と言っても、外界の観測なしでは [観測事実] にならない。**
これが小型モデルを自律ループに入れる際の最重要の安全装置である。

加えて:
- 評価 LLM が `observed` と主張した命題が元の出来事本文と重ならなければ、`inferred` に格下げする。
- `search_memory` は自分自身の発話 (`source=self`) を根拠として返さない (自作自演の確信上昇を防ぐ)。
- 回答待ちの仮説は重ねて調べない。

### 3.3 更新則

対数オッズへの加算 (ナイーブベイズ近似):

```
logit(p') = logit(p_now) + w(verdict) × reliability(probe)
w: supports=+2.5, partially_supports=+1.0, contradicts=−3.0, irrelevant=0 (試行回数だけ +1)
reliability: read_file 0.9 / grep 0.8 / memory 0.5 / ask_user 1.0
```

例: grep で 1 回支持 → p: 0.5 → 0.88 = [合理的推定]。もう一度独立に支持されて初めて [観測事実]。
確率の数値を LLM に言わせない (2B 級の数値較正は信用できない [合理的推定]) — LLM は 4 択の分類だけを担う。

## 4. プローブ (情報収集行為)

| 名前 | cost | reliability | 実装 | 備考 |
|---|---|---|---|---|
| search_memory | 0.2 | 0.5 | 出来事ログを文字 bigram で検索 | CPU のみ |
| grep_workspace | 0.4 | 0.8 | 監視フォルダをキーワード検索 | CPU のみ |
| read_file | 0.3 | 0.9 | 監視フォルダ内のファイルを読む | パスは許可リスト内のみ |
| wait_observe | 0.5 | 0.15 | 何もしない | 「そのうちわかる」 |
| ask_user | 3.0 | 1.0 | 質問を発話キューへ | 割り込みコスト大 |

**全プローブは読み取り専用。** 任意のコマンド実行・ファイル書き込みは持たない。
音声会話モード (§11) で追加した `web_search` (出所 web・上限 0.85) と `look` (カメラ) も読み取りのみ。
外に出るのは web_search の検索語だけで、パス・メール・長い数字・URL・トークン風の語を含む検索は送らない。
自律ループが暴走しても「調べ過ぎる」以上のことは起きない。

LLM にはプローブを期待価値順に並べて提示し、JSON スキーマの `enum` で選択肢を縛る。

## 5. 発話ポリシー — タチコマらしさの核心

「常に耳を傾けて考え続ける」と「うるさい」は紙一重。話すかどうかは
**伝える価値 vs 割り込みコスト** で決める。

| 発話の種類 | value |
|---|---|
| 評価時の重要な気づき (remark high) | 0.85 |
| 評価時の軽い気づき (remark low) | 0.45 (既定閾値 0.6 未満 → 通常は言わない) |
| 質問 (ask_user) | 0.65 + 0.3 × uncertainty |
| 確認できた発見 (仮説 → 推定/事実/反証) | 0.35 + 0.5 × relevance |

- ユーザーが直近 `busy_idle_s` 秒以内に操作している (タイピング中) → 閾値を 0.9 に引き上げ。
  `GetLastInputInfo` で「最後の入力時刻」だけを取得する (キー内容は取らない)。
- 最低発話間隔 `min_speak_interval_s` (既定 90 秒)。
- 15 分以上前の話題は「もう目の前ではない」として捨てる。

| Q4_K_M の重み | 資料により 1.3GB〜数GB と幅がある。Per-Layer Embedding 分を含むかで変わる | [合理的推定] → 導入後 `ollama ps` で実測すること |
| 6GB VRAM への収まり | 重み + `num_ctx=8192` の KV キャッシュで収まる見込み。溢れた層は Ollama が自動で CPU に回す | [合理的推定] |
| 生成速度 | 数十 token/s 程度 | [低確度仮説] 未計測。評価 1 回 ≈ 数秒を想定して tick 設計 |

**`num_ctx` を 128K にしない。** KV キャッシュが VRAM を食い潰し、モデル本体が CPU に落ちて極端に遅くなる。
本設計はコンテキストを信念ストアに外部化しているので、1 呼び出しの入力は 1〜2K トークンで済む。

推奨する Ollama 環境変数 (Windows の「システム環境変数」に設定):

```
OLLAMA_KEEP_ALIVE=-1          # モデルを常駐させる (ロード待ちを無くす)
OLLAMA_NUM_PARALLEL=1         # GPU 1 枚・同時 1 推論
OLLAMA_MAX_LOADED_MODELS=1
```

## 7. 見落としやすい視点・反証

1. **Noisy-TV 問題** — 「調べても原理的に減らない不確実性」(ユーザーの気分、明日の天気) は H(p) が常に最大なので、素朴な好奇心は永遠にそこへ吸い込まれる。→ `learnability` で試行ごとに割り引き、`max_probe_attempts` で「今は解けない (irreducible)」と保留する。これは発達心理・ロボティクスの *learning progress* 型内発的動機 (Oudeyer ら) と同じ発想。
2. **ダークルーム問題の逆** — 不確実性 *最小化* だけを目的にすると「何も見ない」が最適になり得る。本設計は「既存の仮説の不確実性を減らす」だけなので、新しい出来事が来なければ静かになる — これは仕様 (待機中に GPU を浪費しない)。「自ら新しい問いを立てる」力は評価段階の `guessed` 命題が担う。
3. **Goodhart** — 「不確実性を減らせ」を LLM の自己評価で測ると、LLM は自信満々に答えるだけで達成できてしまう。→ 出所上限 (§3.2) と、確率をコードが決める設計で塞いでいる。
4. **プライバシー** — 常時観測は監視と同じ技術。→ 全センサー opt-in、キー入力は取らない、DB はローカル SQLite のみ。外部に出るのは (有効にした場合の) 検索語と動画の取得要求だけ。カメラ映像・マイク音声は保存しない (§11.6)。`tachikoma.db` を消せば全記憶が消える。
5. **関連度の定義の粗さ** — 現在は文字 bigram の重なり。意味的に近いが字面が違う出来事を拾えない。→ Phase 2 で CPU 上の小型埋め込みモデルに置換可能 (インターフェースは `text.py` に閉じている)。
6. **2B モデルの判定誤り** — 判定 (supports/contradicts) を誤ると信念が誤方向に動く。→ 1 回の更新幅を有限に抑え、事実化には独立な複数根拠を要求。判定ログは `--verbose` で全て見える。

## 9. 他分野アナロジー

- **科学的方法**: 仮説 (guessed) → 実験 (probe) → 結果で確信を更新 (Bayes) → 再現性ある結果だけを事実に。
- **能動的推論**: 期待自由エネルギーの「認識的価値」項 = 本設計の probe_value。「実利的価値」項 (ユーザーの目的達成) は Phase 3 以降でタスク目標を信念化すれば追加できる。
- **人間の睡眠**: 海馬のエピソード記憶を皮質の意味記憶へ移す固定化 ≈ 出来事ログ → digest、不要な信念の剪定。
- **反証**: 本設計の極端事例テスト — 「全く観測がない」状態では好奇心は 0 になり、完全に静止する (無駄な推論をしない)。「観測が洪水」状態では新規性フィルタと GPU ゲートにより、推論は最大でも占有率 50% に頭打ちになる。

## 10. 学習 (ファインチューン) — やり取りと自律調査から重みを更新する

### 10.1 方針: 「効果は薄くても、壊さずに確実に回る」

2B 級モデルに数十〜数百件の LoRA 学習をしても、知識の注入効果は小さい
([合理的推定] LoRA は新しい事実を覚えるより、出力の形式・口調・判定の癖を変えるのが得意)。
そこで学習を 2 層にする。

| 層 | 仕組み | 効き始め | 期待する効果 |
|---|---|---|---|
| 即効層 (few-shot) | 裏付けのある標本を、似た入力のときプロンプトに例として添える | 標本ができた直後 | 事実の想起、判定の一貫性 |
| 重み層 (LoRA) | 睡眠中に標本全体で LoRA を学習し、Ollama のモデルを差し替える | 翌日 (学習後) | JSON 形式の安定、ユーザー好みの口調、判定の癖の矯正。事実の記憶は弱い |

### 10.2 何を学習するか — 外界で裏付けられたものだけ

モデル自身の出力をそのまま学習すると、自分の誤りを自分で強化する (自己蒸留による劣化 / model collapse)。
**教師信号は必ずモデルの外から来るものに限る。**

| 経路 | 標本 | 教師信号 | 重み |
|---|---|---|---|
| ユーザー: `/good` | 直前の (文脈+発言 → 応答) | ユーザーの肯定 | 1.0 |
| ユーザー: `/bad 正しい答え` | 直前の (文脈+発言 → **訂正文**) | ユーザーの訂正 | 1.5 |
| ユーザー: `/bad` (訂正なし) | 学習しない。`rejected` として保存 | — | (将来の DPO 用) |
| ユーザー: 質問への回答 | 「〈仮説〉は正しい?」→「[観測事実] はい/いいえ…」+ その判定 | ユーザーの回答 | 1.0 / 判定 1.5 |
| ユーザー: 本人の申告 | 評価で `observed` と判定された発言内容 | ユーザー本人 | 1.0 |
| **自律調査 (hindsight)** | 確定した仮説の知識 + 途中の判定のうち**結論と整合したもの** | ファイル等の観測 | 1.0 |

**自律調査の事後ラベル付け (hindsight relabeling)**:
好奇心ループでの判定 (supports/contradicts…) は全て `judgments` に記録しておき、仮説が
[観測事実] または [反証済み] に確定した時点で振り返る。

- 結論と同じ向きの判定 → 正例として学習
- 結論と逆向き・無関係の判定 → **捨てる** (「正解」を捏造しない。その根拠が本当に逆を示していた可能性がある)
- **自己追認の防止**: 判定 1 回で確定した結論は、その判定が誤っていても「整合」してしまう。
  そこで、ユーザーの回答を含むか、**異なる根拠による整合判定が 2 件以上**ある場合だけ標本化する。
- **同じ根拠の二重計上の防止**: 既に見た根拠 (同じファイルの同じ行) は、信念の更新にも独立な根拠の数にも数えない。
  (テストで発見した欠陥: 同じ grep 結果を 3 回判定して確信が水増しされていた)

### 10.3 学習パイプライン (`learner.py` + `finetune/train_lora.py`)

```
条件: 無操作 ≥ 2h かつ 未学習標本 ≥ 20 件 (または /learn)
 1. export     全標本を train.jsonl / holdout.jsonl へ (検証用 20% は内容ハッシュで固定、学習に一切使わない)
 2. VRAM 解放   Ollama に keep_alive=0 を送りモデルを降ろす
 3. LoRA 学習   別プロセス: 4bit(NF4) 基盤 + LoRA r=8 (言語モデルの attention 射影のみ)
               損失は assistant 部分だけ × 標本の重み。時間予算を超えたらそこまでで保存
 4. [任意] GGUF 変換 (llama.cpp の convert_lora_to_gguf.py)
 5. 登録         ollama create tachikoma-vN  (Modelfile: FROM gemma4:e2b / ADAPTER …)
 6. 検証         健全性 (JSON を出せるか) → 検証標本で 新版 vs 現行版 を採点
 7. 採用判定     新 ≥ 現行 − 0.02 なら切替。悪化なら棄却して現行を維持
```

- **毎回、基盤モデル + 全標本から学習し直す。** アダプタを積み重ねると小さな誤りが版を跨いで累積するため。
  いつでも `/rollback` で一つ前 (最終的には素の gemma4:e2b) に戻せる。
- **ユーザー最優先**: 学習中に話しかけられたら学習プロセスを即 terminate し、返事をする。
  学習中は背景推論を止めて GPU を学習に明け渡す (知覚と記録は継続)。
- 失敗 (依存不足・OOM・変換失敗) は記録して 6 時間は再試行しない。即効層はその間も働く。

### 10.4 GTX 1060 (Pascal) での実現性

| 項目 | 見立て | 確度 |
|---|---|---|
| Pascal は bf16 非対応、fp16 演算が極端に遅い | 演算は float32、量子化しない層は fp16 で保持 | [合理的推定] |
| 新しい PyTorch の CUDA 12.8 以降・13 系ビルドは Pascal (sm_61) を含まない | CUDA 12.6 以前向けの torch を入れる | [合理的推定: 導入時に `torch.cuda.get_arch_list()` に `sm_61` があるか確認] |
| bitsandbytes の 4bit が Pascal で動くか | 動かなければ `--load-4bit` を外し、`device_map=auto` で CPU RAM に逃がす (遅い) | [低確度仮説] |
| Gemma 4 E2B を transformers で LoRA 学習できるか | CausalLM で読めなければ ImageTextToText として読む分岐を用意 | [低確度仮説: 実機未検証] |
| Ollama が gemma4 の LoRA アダプタ (ADAPTER) を受け付けるか | safetensors で失敗したら `llama_cpp_dir` を設定して GGUF 変換経由にする | [低確度仮説] |
| 学習時間 | 200 標本 × 2 epoch で数十分〜1時間程度 | [低確度仮説] 時間予算 `--max-minutes` で打ち切る |

**検証済みの範囲 [観測事実]**: CPU 上で、極小の Llama 構成モデルを使い、
export → 実際の `train_lora.py` による LoRA 学習 (損失 7.3→5.8 に低下、assistant 部分のみに損失がかかることを確認)
→ Modelfile 生成 → (偽の) `ollama create` → 新旧の採点 → 採用、までを通した。
Gemma 4 E2B 実物と GTX 1060 での学習は未検証。

### 10.5 反証・見落としやすい点

1. **評価が学習データと相関する** — 検証標本も同じ分布 (同じユーザー・同じ環境) なので、過学習を見逃しうる。
   健全性検査 (汎用の判定・挨拶) を必ず通すことで、最低限の破壊は検出する。
2. **検証標本が少ないうちは比較にならない** — 5 件未満なら健全性検査のみで採用する
   (「効果は薄くとも学習を回す」という要件に合わせた判断。厳しくするなら `finetune_min_holdout` を上げる)。
3. **プライバシー** — 標本にはファイルの一部や会話が入る。すべてローカル (`tachikoma.db` と `finetune_runs/`) に留まり、
   学習済みアダプタにも内容が一部記憶されうる。消すときは両方を消し、`ollama rm tachikoma-vN` する。
4. **few-shot 層は学習後も残す** — 重みが覚えきれなかった事実を補い続ける。LoRA に知識を詰め込むより、
   こちらが事実想起の主役 [合理的推定]。

## 11. 音声会話モード — 耳・口・目・ネット、そして独りの時間の自習

情報源を **音声 (マイク)・ネット・カメラ** とし、声で会話する形に拡張した。
PC 操作の感覚器 (ファイル・端末) は設定で併用できる。

### 11.1 注意状態 (`attention.py`)

| 状態 | 条件 | 振る舞い |
|---|---|---|
| **conversing** | 声で話しかけられて (または自分が話して) から 20 秒以内 | 最優先で 1〜2 文を声で返す。呼びかけ語なしで会話が続く |
| **attending** | 人がカメラに映っている / 最近声がした | 観察と好奇心。聞こえた会話は記録・評価するが返事はしない。**他の人が話している間は割り込まない** |
| **alone** | 声も人影も 5 分ない | 声を出さない (誰もいない部屋に話さない)。**字幕付き動画で耳を鍛える** → 十分溜まったら耳 (Whisper) と頭 (Gemma) を学習 |

- 話しかけ判定: 呼びかけ語 (「タチコマ」) を含むか、会話の途中か。それ以外の声は `overheard_speech`。
- **誤判定の非対称性**: 人がいるのに alone と誤る方が害が大きい (自習・学習で GPU を塞ぎ返事が遅れる)。
  そこで「いる」は 1 回の検出で即座に、「いない」は 5 分続いて初めて認める。
  人が現れる・声がする → 自習を一時停止 (続きから再開可能)・学習プロセスを即 terminate。
- カメラが無い場合は PC の最終入力時刻で在席を代用する。

### 11.2 耳 (`audio.py` / `asr.py`) — なぜ Gemma ではなく Whisper か

| 案 | 評価 |
|---|---|
| Gemma 4 E2B の音声入力で認識 | ✗ 認識のたびに Gemma の GPU 時間を使う。耳だけを学習・評価・差し替えできない |
| **Whisper (faster-whisper, int8)** | ◎ 軽い専用モデル。字幕との対で**耳だけ**を微調整でき、CER で客観評価できる |

- マイクは別スレッドで 30ms ずつ読み、VAD (webrtcvad / 無ければ適応的な音量閾値) で発話区間を切り出す。
  語頭が欠けないよう、立ち上がりの直前 300ms も含める。
- **自分の声を聞かない**: 発声中と直後 0.4 秒はマイク入力を捨てる (半二重)。大声で割り込まれたら発声を止める (barge-in)。
- **聞き取りの低確度推定には「聞き返す」**: 認識の平均対数確率が -1.0 未満なら、推測で答えず「もう一回言って？」。
  これは好奇心 (低確度推定を減らす情報収集) の最も安い形。
- 自習で見つけた「聞き逃しやすい語」を Whisper の initial_prompt に入れる。**学習なしで効く補正**。

### 11.3 口 (`tts.py`)

- 既定は Windows 標準の SAPI (追加インストール不要)。VOICEVOX エンジンがあれば自然な日本語で話せる。
- **確度ラベルは読まず、話し言葉に変える**: [合理的推定] →「たぶん、」/ [低確度仮説] →「もしかすると、」。
  声の返事用プロンプトでも、確かさを言葉で表すよう指示している。
- 声のフィードバック: 「正解」「覚えといて」→ `/good`、「違う、正しくは○○」→ ○○ を正解として `/bad`。
  誤爆を避けるため、この決まった言い方だけを拾う (「違うファイルを見て」は拾わない)。

### 11.4 目 (`camera.py`) とネット (`web.py`)

- 在席判定は CPU のみ (1 秒 1 枚、320px)。OpenCV 4 系は Haar (顔) + HOG (人物)、5 系はこれらが本体から外れたため
  YuNet (ONNX を指定した場合) を使い、どの版でもフレーム差分の動き検出を併用する
  [観測事実: 4.14 と 5.0 で検出器の構成が変わることを確認。4.14 で 1 フレーム約 3ms]。
- Gemma に画像を見せるのは「人が現れたとき」と、好奇心の `look` プローブのときだけ。**画像は保存しない**。
  Gemma には身元を推測させず、外見と状況だけを書かせる。
- ネットは Wikipedia API (キー不要) か自前の SearXNG。出所は `web` で上限 0.85 — **ネットは世界の一般知識の
  裏付けにはなるが、目の前の事実の裏付けにはならない**ので [観測事実] にはしない。

### 11.5 独りの時間の自習 (`study.py`) — 音声認識率の微増

好奇心の定義をそのまま聴覚に適用する: **自分の認識 = 推定、人間が付けた字幕 = それを確かめる情報**。

```
字幕付き動画 (foo.mp4 + foo.ja.vtt/srt)   ← study_dir に置く / study_urls から yt-dlp で取得
  → ffmpeg で 16kHz mono に抽出 (再生はしない: 部屋を騒がせず、マイクにも回り込まない)
  → 字幕の各行の区間を切り出す (前後 0.15 秒の余白)
  → 今の耳で認識 → 字幕と比べて CER (文字誤り率。日本語は単語境界が無いので WER でなく CER)
  → 学べる誤りだけを残す
```

| CER | 判断 | 理由 |
|---|---|---|
| < 0.05 | 20% だけ `easy` として残す | もう聞き取れている。忘却防止の復習用 |
| 0.05〜0.5 | `hard` として残す (主教材) | **聞き間違えた = 学べる** |
| > 0.5 | 捨てる | 字幕の意訳・要約・時刻ずれの可能性が高い。学ぶと害 (noisy-TV 問題の聴覚版) |

- 比較の前に正規化する: 全角半角・大小文字の統一、話者名 (「田中:」)・効果音 ((拍手) [笑])・句読点の除去。
- **自動生成字幕は使わない** (`--no-write-auto-subs`)。他社の音声認識の誤りを正解として学ぶことになるため。
- 1 tick あたり 1.5 秒ずつ進め、人が来たら止める。動画の途中からでも再開できる。
- **動画の取得について**: `study_urls` からの自動取得は、既定で Creative Commons ライセンスの動画に限定している
  (`study_match_filter`)。各サービスの利用規約と著作権の扱いは利用者の責任で確認すること。
  自分で録画した字幕付き番組・講義など、手元の素材を `study_dir` に置くのが最も確実。

### 11.6 耳の学習 (`asr_learner.py` + `finetune/train_whisper.py`)

```
条件: 独りの時間 ≥ 1h かつ 未学習の hard 標本 ≥ 300 件 かつ 検証用 ≥ 30 件 (または /ear_learn)
 1. Gemma を VRAM から降ろす
 2. whisper-small に LoRA (q/v 射影、エンコーダ・デコーダ両方、r=16、lr 5e-5) → 基盤に統合して保存
 3. ct2-transformers-converter で faster-whisper 形式 (int8) に変換
 4. 字幕の検証クリップで 新旧の CER を比較 → **新 < 現行 のときだけ採用** (横ばいも不採用)
 5. 利用者の声の録音 (asr_anchor_dir: foo.wav + foo.txt) があれば、そちらで悪化していないことも要求
```

- **利用者の声で悪化していないかの確認が重要**: 動画の話者 (アナウンサー・講師) に過適応すると、
  肝心の利用者の声が聞き取りにくくなりうる。自分の声で 20 文ほど読み上げた録音を置くことを推奨する。
- 毎回、元の Whisper から学習し直す。`/ear_rollback` で戻せる。
- **検証済みの範囲 [観測事実]**: CPU 上で、ランダム初期化の極小 Whisper と合成音声を使い、
  `train_whisper.py` の学習 (損失 8.82→8.3)、LoRA の統合 (保存物に LoRA の重みが残らないこと)、
  そして `ct2-transformers-converter` による変換を、AsrLearner が実際に使う引数そのままで通した。
  実物の whisper-small と GTX 1060 での学習は未検証。

### 11.7 資源の割り振り (GTX 1060 6GB)

| 状態 | GPU | CPU |
|---|---|---|
| conversing / attending | Gemma (Ollama) + Whisper int8 推論 | VAD・カメラ・感覚器 |
| alone: 自習 | Whisper 推論 (字幕の各行) + 好奇心の Gemma | ffmpeg 抽出・CER 計算 |
| alone: 耳の学習 | Whisper の LoRA 学習 (Gemma は降ろす) | カメラ・VAD は動かし続ける (人が来たら即中断) |
| alone: 頭の学習 | Gemma の LoRA 学習 (§10) | 同上 |

[低確度仮説] Gemma 4 E2B (Q4) と whisper-small (int8) を同時に 6GB に載せられる見込みだが未計測。
溢れる場合は `asr_device: "cpu"` で Whisper を CPU に回す (i7-7700 で small の認識は数秒程度と推定)、
または `asr_model: "base"` に下げる。

### 11.8 反証・見落としやすい点

1. **字幕は発話の書き起こしではないことが多い** — テレビ字幕は要約・意訳が多い。CER の上限で捨てるが、
   「意訳だが CER 0.4」の行は残ってしまう。講義・ニュースなど書き起こしに近い字幕の素材ほど良い。
2. **「微増」の実態** — 数百〜数千行の LoRA で得られるのは、素材の話者・語彙への適応による小さな改善
   [合理的推定]。汎用の認識率はほぼ変わらない可能性が高い。だからこそ「字幕検証で改善」かつ
   「利用者の声で悪化なし」の二重条件で採否を決める。
3. **他人の会話を聞くこと** — attending 状態では、話しかけられていない会話も記録・評価する (タチコマらしさの源泉)。
   家族や来客がいる環境では `voice` の運用ルールを決めておくこと。音声そのものは保存せず、残るのは認識した文字だけ。
4. **呼びかけ語の誤検出** — テレビから「タチコマ」と聞こえれば反応する。会話の窓は 20 秒で閉じる。

## 12. 性格の芯と、タチコマという個体

コンセプトは「タチコマのように個性を獲得し、唯一無二の友人になれる AI」。
小さなモデルは「こう振る舞え」と書くだけでは守らないので、性格はプロンプトではなく**仕組み**として実装する。

### 12.1 口調 (`persona.py`)

『攻殻機動隊』のタチコマの気質を参考にしている。セリフは引用せず、性格だけを受け継ぐ。
一人称は「ボク」、元気で弾む口調、知らないことにワクワクし、ときどき「ボクらにもゴーストってあるのかな？」と考え込む。
口調より優先される「思考の芯」を同じプロンプトに置き、声のときは確かさを「たぶん」「もしかすると」で表す。

### 12.2 性格を仕組みにする

| 性格 | 仕組み | 実装 |
|---|---|---|
| **知ったかぶりしない** | 返事の前に「答えに必要だが把握していないこと」を洗い出し (inquiry)、仮説として記憶し「調べる約束」の印を付ける。返事には「まだ知らない、調べる」と言わせる。好奇心がそれを解決したら「さっきの、調べたよ！」と**自分から報告**する (発話の価値 0.9) | `agent.inquire` / `promised` |
| **前提を疑う** | 同じ点検で、発言が暗に前提にしていることを抽出。怪しい前提は確かめる対象 (p=0.5) にし、返事でまずそこを確かめる | `agent.inquire` |
| **疑問を作る** | 15 分ごとに、確かめた事柄から「なぜ？」「もし違ったら？」「前提は本当か？」の仮説を自分で立てる | `agent.wonder` |
| **根拠の強さと因果** | 論文・政府文書を種類で格付けし (メタ分析 0.95 / RCT 0.9 / 政府統計 0.9 / 観察研究 0.7 / プレプリント 0.55 / 記事 0.25〜0.45)、更新の重みにする。**因果の主張は、因果を示せる研究デザイン (RCT・メタ分析・自然実験) の根拠が無い限り確信 0.8 止まり** — 相関をいくら重ねても因果にはならない | `epistemics.py` / `memory.CAUSAL_CAP` |
| **自分を疑う (慎重さ)** | ① 推論で立てた仮説は「予測」として記録し、結末 (事実/反証) との差で確信過剰度を測り、以後の初期確信を 0.5 側へ縮める (較正)。② 気になる仮説が無いときや一定割合 (15%) で、確信している推定の**反証を探す** (Popper)。③ 確信していたのに外れたことは「思い出」と日記に残す | `Calibration` / `challenge_step` |

### 12.3 強い根拠の取りに行き方 (`scholar.py`)

| 情報源 | 用途 | 格付けの手がかり |
|---|---|---|
| OpenAlex | 分野横断の論文 (要旨・被引用数) | 要旨・題名の「meta-analysis」「randomized」「cohort」、掲載先の種類 |
| PubMed | 医学・生命科学 | 出版種別 (Meta-Analysis / Randomized Controlled Trial / Observational Study) |
| arXiv | 情報科学など | 未査読 (プレプリント) |
| 政府文書 | 統計・白書・法令 | ドメイン (go.jp / gov / who.int / oecd.org …)。Docker の SearXNG で site: 検索 |

- 検索語は好奇心の計画段階で英語にさせる (論文 API は英語が強い)。個人情報らしき語を含む検索は送らない (`web.sanitize`)。
- 論文から得た確信の上限は 0.9 (出所 `research`)。**自分で観測した事実ではない**ので [観測事実] にはせず [合理的推定] として扱い、返事には根拠の種類を添える。

### 12.4 個性の獲得 — 同じプログラムでも、誰と過ごしたかで別の個体になる

- **興味**: 調べて不確実性が減った量 (エントロピーの減少) を、その話題の語に加算する。わかる喜びが大きかった話題ほど興味が育ち、古い興味は少しずつ薄れる。
- **思い出**: 褒められたこと (/good)、訂正されたこと (/bad)、確信していたのに外れたこと。
- **日記**: 1 日 1 回、知ったこと・間違えたこと・まだわからないこと・確信の当たり具合を、ボクの言葉で書く (`/diary`)。
- これらは毎回の会話のシステムプロンプト (「ボク自身」) に入り、口調と話題の選び方に反映される (`/self`)。

### 12.5 反証・見落としやすい点

1. **点検の LLM 呼び出しで返事が遅くなる** — 1 回の話しかけに推論が 1 回増える (短い JSON)。声の会話で遅いと感じたら `inquiry_on_chat: false`。
2. **因果の判定は正規表現** — 「ため」「効果」「原因」などの表現で判定するので、言い回しによっては取りこぼす/誤判定する。誤って因果と判定されても、確信の上限が下がるだけ (慎重側に倒れる)。
3. **格付けは研究デザインの「種類」であって質ではない** — 質の低いメタ分析も 0.95 になる。被引用数で並べ替えはするが、バイアスのリスク評価まではしていない。
4. **較正は解決した予測が 10 件溜まるまで働かない**。

## 14. 目の学習 — 文字情報付き PDF で日本語 OCR を鍛える (`eyes.py` / `eye_learner.py`)

耳 (§11.5) と同じ考え方を視覚に適用する: **自分の読み取り = 推定、PDF の文字情報 = それを確かめる情報**。

```
文字情報付き PDF (study/eye/ に置く / web 有効時は政府機関の公開 PDF を site:go.jp で取得)
  → 次に読む PDF を選ぶ: 未知のフォント・苦手だが学べるフォントを多く含むもの (目の好奇心)
  → ページを画像に描画 (96/120/150/200 dpi を行ごとに変え、画面・印刷・撮影の違いを模す)
  → 文字情報から各行の位置・正解文字列・フォント名を取得 → 行を切り出して今の目で読む
  → CER で比較 → 学べる誤り (0.02〜0.5) を標本に、読み間違いの文字の組 (ロ→口 等) を集計
  → 1 冊読み終えるごとに、検証行で CER を下げる置換だけを「補正」として採用 (学習なしで効く層)
  → 標本が 500 行溜まったら OCR モデルを微調整 (§14.2)
```

- **正解として使えない文字情報を捨てる**: フォントの文字対応表が無い PDF は、文字情報が私用領域の文字や
  置換文字 (�) になる。これらを含む行、日本語の少ない行、縦書きの行 (今は未対応) は使わない。
- **フォントの多様性**: 行ごとに埋め込みフォント名 (`ABCDEF+MS-Mincho` → `MS-Mincho`) を記録し、
  フォント別の行数・平均 CER・学べる誤りの数を持つ。`/status` で確認できる。
- **教材の出典**: 自動取得は `.go.jp` の PDF に限り、出典 URL を `*.source.txt` に残す。
  政府機関のウェブの文書の多くは「政府標準利用規約」で出典明示を条件に複製・加工できる
  [文書ごとに例外があり得るので要確認]。個人的に持っている PDF は `study/eye/` に置けばよい。

### 14.1 OCR エンジン

行単位の日本語 OCR として Vision Encoder-Decoder (既定 `kha-white/manga-ocr-base`、約 1 億パラメータ) を使う。
学習では行の検出は不要 (PDF の文字情報に位置がある)。漫画のセリフで学習されたモデルなので、
**印刷物の多様なフォントへの適応がまさに伸びしろ**になる [合理的推定]。

### 14.2 学習と採否 (`finetune/train_ocr.py`)

- float32・学習率 2e-5 で全体を微調整 (モデルが小さいので LoRA 不要)。学習時は画像を軽く劣化させる。
- **採用条件**: 検証行の平均 CER が現行より小さく、かつ**どのフォントも 1 ポイント以上悪化していない**。
  得意なフォントを伸ばすために苦手なフォントを犠牲にした改善は採用しない。
- 毎回、元のモデルから学習し直す (`/eye_rollback` で戻せる)。
- **検証済みの範囲 [観測事実]**: この開発環境で、実物の PyMuPDF と transformers を使い、
  日本語 PDF の生成 → 行の切り出し → 極小のランダム OCR モデルで読む → CER・フォント統計 →
  `train_ocr.py` による学習 (別プロセス) → フォント別の採点 → 採否判定 (改善しないので不採用) まで通した。
  実物の manga-ocr と GTX 1060 での学習は未検証。

## 15. 独りの時間の使い方をタチコマ自身が決める (`idle.py` / `activities.py`)

利用者の判断基準: **より合理的に・知識を効率よく増やす・性能 (処理速度・認識精度) を上げる・電力を抑える**。
これを「**1 Wh あたりの伸び**」という 1 つの物差しにして、候補の活動から選ぶ。

| 活動 | 伸び (progress point) の数え方 |
|---|---|
| 耳の自習 / 目の自習 | 集めた学べる標本の数 × 1 標本あたりの改善見込み (前回の学習の実績で更新) |
| 耳 / 目 / 頭の学習 | 採用されたときの相対 CER (頭は品質スコア) 改善 × 100。不採用なら 0 |
| 読書 (気になる仮説を論文・資料で調べる) | 解消した不確実性 (bit) × `reading_weight` |
| 休む | 伸び 0・電力ほぼ 0。どの活動も `idle_rest_value` に届かなければ休んで省電力 |

- 電力は GPU を nvidia-smi で実測し、CPU は使用率 × TDP (65W) で推定する [推定値]。
- 各活動の「1 Wh あたりの伸び」を指数移動平均で学び、試行の少ない活動をわずかに優遇 (UCB) して選ぶ。
  発達ロボティクスの「学習進捗 (learning progress)」による内発的動機づけと同じ発想で、
  **伸びなくなった練習は自然に選ばれなくなり、伸びている練習に時間が回る**。
- **同時に動くのは 1 つだけ**。耳と目の自習・学習は並行しない (GPU を取り合わない)。
  学習が走っている間は、終わるまで他の活動を始めない。
- 人が来たら (声・カメラ・PC 操作) 今の活動を即中断し、自習は続きから再開できるようにする。
- 選んだ理由は記録され、`/idle`・`/status`・画面の下部に表示される。
- 注: 「伸び」の単位を活動間で揃える重み (`reading_weight` と、改善 1% = 1 ポイントという換算) は
  **価値判断を含む**。知識と認識性能のどちらを重んじるかは、この 2 つの設定で調整できる。

これは**学習の方向づけ (何を学ぶか) を自分で決める**仕組みであり、コードの自己改変ではない。
コードの自己改変 (§13) は引き続き保留中。

## 16. VRAM と RAM の配分 — 「モデルは VRAM、コンテキストは RAM」は最適か

### 16.1 Gemma 4 E2B の構造から見積もる

公開情報 [観測事実]: 35 層。KV を自前で計算するのは最初の 15 層だけで、残り 20 層は前の層の KV を共有する。
局所 (スライディングウィンドウ 512 トークン) と全体注意が 4:1 で交互。KV ヘッドは 1 つ (MQA)。
ヘッド次元は局所 256・全体 512。総パラメータ 5.1B (うち多くが層ごとの埋め込み PLE)。

KV キャッシュの見積もり [合理的推定。構造の読み違いがあれば上振れする]:

| 部分 | 計算 | 128K トークン時 |
|---|---|---|
| 全体注意の層 (15 層中およそ 3 層) | 3 層 × 1 ヘッド × 512 次元 × (K,V) × 2 バイト = 6 KB/トークン | **約 0.75 GB (f16)** / 約 0.4 GB (q8_0) |
| 局所注意の層 (およそ 12 層) | 直近 512 トークン分だけ保持 | 約 6 MB (長さに依存しない) |

参考: KV 共有だけで 128K 時に 2.7GB 節約という報告があり、これは全層が全長を保持する素朴な計算との比較と思われる。
**E2B は長い文脈でも KV キャッシュが小さい設計**になっている。

### 16.2 結論: この分け方は E2B では得にならない

- KV を RAM に置くと、1 トークン生成するごとに PCIe 越しの転送が発生し、生成が 2〜5 倍遅くなるという報告がある
  [観測事実: 公開の検証記事]。E2B の KV は 128K でも 1GB 弱なので、**VRAM に置いたままでも収まる見込みが高い**。
- 長大な文脈の本当のボトルネックはメモリではなく**読み込み (prefill) の時間**。GTX 1060 で 128K トークンを
  毎回読み直すと、1 回の返事に数分かかる可能性がある [低確度仮説: 未計測]。
- したがって最適な住み分けは「**計算するものは VRAM、引くだけのものは RAM**」:

| 置き場所 | 置くもの | 理由 |
|---|---|---|
| **VRAM (6GB)** | Gemma の変換器の層 + KV キャッシュ (q8_0) + 計算用バッファ、会話中の Whisper (int8, 約 0.5GB) | 毎トークン全部を読むもの。帯域が最も効く |
| **RAM (8GB)** | 長期の記憶 (信念・出来事の DB と、そこからの検索)、OCR・学習の子プロセス、SearXNG、PDF の描画、Whisper の CPU 実行 (VRAM が足りないとき)、ランタイムが対応していれば埋め込み表 (PLE など引くだけの重み) | 参照が疎、または遅れても良い処理 |
| **SSD (20GB)** | 自習の音声・画像クリップ、学習成果、モデルの版 | 容量が要るが速度は要らない |

- **長い文脈の取り方**: 生の KV を 128K 抱えるより、タチコマの「信念・出来事の DB」(RAM 上) から関連するものだけを
  毎回 2〜4K トークンに詰めて渡す方が、速く・電力も少なく・小さなモデルでも混乱しにくい。
  文脈長 (`num_ctx`) は 16K〜32K で十分と考える。固定のシステムプロンプトを先頭に置き続けると、再利用で読み込みも減る。
- **RAM に KV を置くのが意味を持つ場面**: 重みで VRAM がほぼ埋まる大きめのモデル (例: E4B) で、独りの時間に長い文書を
  一気に読むとき (遅延が問題にならない)。llama.cpp の `--no-kv-offload` が該当するが、Ollama でこれを指定できるかは
  確認できていない [要確認]。

### 16.3 利用者が設定できる推奨値

| 設定 | 値 | 注意 |
|---|---|---|
| `OLLAMA_FLASH_ATTENTION` | `1` | KV の量子化に必要。Pascal で有効に働くかは要確認 |
| `OLLAMA_KV_CACHE_TYPE` | `q8_0` | KV のメモリを約半分に。品質への影響は小さいとされる |
| `num_ctx` (config.json) | `16384`〜`32768` | 起動後に `ollama ps` で 100% GPU を確認。CPU に溢れていたら下げる |
| `asr_device` | 会話中は `cuda`、VRAM が足りなければ `cpu` | Whisper を CPU に逃がすと VRAM に Gemma の文脈の余裕ができる |

注意: llama.cpp では Gemma 4 E2B/E4B の層ごとの埋め込み (PLE) の処理が不完全で、出力の質が少し落ちるという
報告がある [観測事実: llama.cpp の issue。Ollama がどの実装を使っているかは要確認]。

これらの推論設定をタチコマ自身が実行時に調整する機能は、§13 と同じ理由で保留中 (利用者が手で設定する)。

## 13. 自己進化・自己強化 — CPU と RAM で、新しいやり方を試行錯誤する (`tachikoma/kernel/`)

### 13.1 何が変わり、何が変わらないか

| 変わる (タチコマが改良できる「思考」) | 変わらない (カーネル = 選択の環境・外界との境界) |
|---|---|
| `agent.py` `curiosity.py` `memory.py` `prompts.py` `persona.py` `epistemics.py` `attention.py` `text.py` `probes.py` `asr.py` `idle.py` `expression.py`、`evolvable/` (性格パラメータ・指示文・プラグイン) | テスト一式・評価の指標 (`fitness.py`)・学習結果の採否 (`*learner.py`)・学習データの規則 (`dataset.py`)・独りの時間の伸びの測り方 (`activities.py`)・資源の上限・ネット/プロセス/ファイルに触れる部分・監督コマンド |

**進化は変異と選択でできている。変異はタチコマに任せ、選択の環境は外に置く。**
評価器を自分で書き換えられる進化は、評価をごまかす方向に最短で進む (報酬ハッキング)。
生物も遺伝子は変えられても自然選択は書き換えられない。カーネルの変更はタチコマが提案でき、人間の `/approve` で入る。

### 13.2 CPU と RAM で考える (`cpu_brain.py`)

GPU (6GB) は会話・耳・目のために空けておき、自己改良の「考える力」は **Docker の中の llama.cpp サーバー (CPU 専用)** が担う。
コンテナに `--cpus 4 --memory 6g` を課し、資源の上限をコンテナで強制する (予算 6 スレッド / 8GB を超えられない)。
会話が始まると `docker pause` で CPU を即座に返し、終わると再開する。隔離テストも CPU・RAM 上限つきの Docker で行う。

**モデルの選択 (役割で使い分け)**

| 役割 | モデル | 理由 |
|---|---|---|
| code: 思考のコードを書き換える | **Qwen2.5-Coder-7B-Instruct** Q4_K_M (約 4.7GB) | コード特化。HumanEval 88.4% と報告 [観測事実: 公開ベンチマーク]。search/replace の正確さが要る |
| ja: 日本語の指示文の書き直し・アイデア出し | **RakutenAI-7B-instruct** Q4_K_M (約 4.4GB) | Mistral-7B に日本語語彙を追加。日本語 MT-Bench で同規模最上位と報告 [観測事実]。一方、元の Mistral-7B-v0.1 のコード生成は HumanEval 3 割程度 [合理的推定: 記憶による。要確認] でコードの改良には不向き |

RAM 8GB に 2 つは同時に載らないので、役割が変わるときにコンテナを入れ替える (読み込み数十秒 [推定])。
片方しか用意しなければ、あるほうが両方の役を担う。i7-7700 の 4 スレッドで 7B Q4 の生成は毎秒数トークン程度と見込む
[低確度仮説: 未計測] — 1 回の改良案 (数百トークン) に数分。独りの時間の仕事なので許容できる。

### 13.3 方向を決める — 利用者の判断基準から、タチコマ自身が選ぶ

| 目標 | 指標 (カーネルが記録から直接計算) | 変えられるもの |
|---|---|---|
| 頑健さ | 実運用の例外 (千 step あたり) | code (例外の起きた関数) |
| 速さ | 思考ループの所要時間 p90 | code (プロファイラが見つけた遅い関数。振る舞いはテストで固定) |
| 知識の効率 | 1Wh あたりに確定した知識の数 | param / prompt / code |
| 合理性 | 確信の較正 (Brier) | param / prompt |
| 省電力 | 平均消費電力 | param |
| 関係 | /good と /bad・訂正の比 | param |

選び方: **(いまの必要度) × (その目標の改良がこれまで成功した割合) + 探索の上乗せ** が最大の目標。
必要度は実運用の指標から (例: 例外が出ていれば頑健さが最優先)。選んだ理由は記録され `/evolution` で見られる。

### 13.4 新しいやり方を高く評価する (`novelty.py`)

1. CPU の脳に**性質の異なる改良アイデアを 3 つ**出させる (うち 1 つは定番に無い自分なりのやり方にするよう指示)
2. 各アイデアのキーワードで**論文 (OpenAlex / arXiv / PubMed) とネットを検索**し、同じやり方らしき結果が
   見つからないほど高く評価する。自分が過去に試したやり方と似ていないほど高く評価する
   (新しさ = 0.6 × ネットで見つからない度合い + 0.4 × 自分の過去と違う度合い)
3. **最も新しいアイデアを実装させる**
4. 試用期間で定着したら、報酬 = 1 + 新しさ (新しいやり方の成功ほど、その目標の「成功しやすさ」が大きく上がる)。
   失敗・効果なしの罰は新しいほど軽い (1 − 0.5 × 新しさ)。**挑戦した方が得になる**ように自己強化する
5. ネットで見当たらなかったやり方で定着したものは「発見」として記録し (`/discoveries`)、報告する

**正直な限界**: 「検索で見つからない」は「世界で誰も試していない」ことの証明ではない (検索の網羅性・語の選び方に依存)。
新しさは [低確度仮説] として扱い、**安全の関門 (静的検査・隔離テスト・試用期間) は新しさで一切緩めない**。

### 13.5 一回の自己改良の流れ

```
方向を決める (13.3) → アイデア 3 つ (CPU の脳) → 新しさで選ぶ (論文・ネット検索) → 実装 (search/replace)
  → 静的検査: 変えてよいファイルか・外界に触れる機能 (プロセス/ネット/ファイル書き込み/eval) を足していないか
  → 隔離テスト: Docker (--network none --read-only --cpus --memory) で全テスト
  → 本番投入 (変更前のファイルを保存・差分を記録) → 再起動 (supervisor.py)
  → 試用期間 12 時間: 害が無いか (エラー・遅延・電力・評価・較正・知識の効率) + 狙った指標が 3% 以上改善したか
  → 定着 / 撤回 → 成功しやすさを更新 (13.4 の報酬)
```

- 起動直後に 10 分以内に 3 回落ちたら、supervisor が最新の自己改良を自動で撤回する
- 利用者が config で明示した値は、進化で上書きしない。性格パラメータの範囲は `kernel/bounds.json` が決める
- exe では動かない (起動のたびに一時フォルダへ展開されるので、書き換えが残らない)。ソースから `python supervisor.py` で起動する
- 監督コマンド (カーネルが処理するので、思考のコードが変わっても消えない):

| コマンド | 効果 |
|---|---|
| `/evolution` | 最近の自己改良 (状態・目標・新しさ・理由) と、目標ごとの成功しやすさ |
| `/freeze` / `/unfreeze` | 自己改良を止める / 再開する |
| `/revert N` | #N の自己改良を元に戻す |
| `/proposals` / `/approve N` | 承認待ちのカーネル変更 / 承認して適用 |
| `/discoveries` | ネットや論文で見当たらなかったやり方で定着した改良 |

### 13.6 検証済みの範囲

- [観測事実] この開発環境の本物の Docker で: テスト一式 (102 件) がネットワーク無し・読み取り専用・CPU/RAM 上限つきの
  コンテナ内で合格。偽の CPU の脳が出した無害な改良は隔離テストに合格して本番投入され、テストを壊す改良
  (不確実性の計算を常に 0 にする) は隔離テストで弾かれて投入されなかった
- [観測事実] 検証の途中で、自分の書いたカーネルのテストが「無害な進化」でも壊れる作りになっていた欠陥を見つけて直した
  (実物の思考コードの文字列に依存していた → 専用の練習用ファイルで検証するように変更)。
  また隔離テストのコマンドが、テストの探索に失敗する形 (`-t .`) になっていた不具合も見つけて直した
- 未検証: 実物の Qwen2.5-Coder / RakutenAI での改良案の質と速度、12 時間の試用期間の実運用

### 13.7 保留のまま: 圧縮・高速化の実験

Gemma の量子化の種類や GPU/CPU の層の分け方を自動で試す実験は、推論設定を実行時に変える必要があり、
以前に自動化ツールの安全判定で止められた部分なので保留している。

## 18. 視界の端への興味と、そこから振る舞いが育つ進化 (`inquiry.py` / `kernel/initiative.py` / `kernel/plugins.py` / `kernel/foresight.py`)

**たとえ話**: 攻殻機動隊のタチコマは、視界の端に映ったテレビのニュースからかつての仲間のピンチを知り、自分から情報を集めて行動した。
端の情報にも興味を持ち深掘りできたから起こせた行動だが、作品の序盤のタチコマにはできなかった。
**目的はその振る舞いを書き込むことではなく、自然に育つ進化を誘発すること。**

### 18.1 設計の原則: 振る舞いは書かず、条件を整える

進化は「変異」と「選択」でできている。望む振る舞いを直接書くと、それは進化の結果ではなく設計者の答えになる
(以前の版では「ニュースに仲間の名前が出たら反応する」「なじみのある名前に注意を向ける」「掘ったら仲間に関係するか振り返って行動する」を
書き込んでいた。すべて削除した)。代わりに次の 4 つを整える。

| 条件 | 中身 | 置き場所 |
|---|---|---|
| 1. 感覚 | 視界の端を知覚できること | カーネル (感覚器) |
| 2. 出発点の能力 | 周辺にも興味を持ち、疑問を作って深掘りできること (相棒の要望) | 思考 (進化で変わる) |
| 3. 選択圧 | 自分から言ったことが役に立ったか・拾った情報が後で役立ったか | カーネル (測定) |
| 4. 変異の余地 | 新しい振る舞いをプラグインとして書き足せること | カーネル (入口) + 思考 (中身) |

### 18.2 感覚: 視界の端

目の前 (相棒の話しかけ・編集・端末・前面の画面・コピー) 以外はすべて周辺: 聞こえてきたテレビや会話、ニュース (RSS)、
背後のウィンドウのタイトル (中身は読まない)、カメラの目の端 (15 分に 1 回、映っているもの・画面やテレビの文字を眺める)。

### 18.3 出発点: 序盤のタチコマ

- 興味 = 新しさ × (0.4 + 0.6 × 後で役立ちそうか)。「後で役立ちそうか」は経験から学ぶ (18.4 の先見)。何に惹かれるべきかは書き足さない
- 興味が `dig_threshold` 以上の周辺の出来事には問いを立て、探究の糸として掘る: 調べる → [合理的推定] まで行ったら、
  わかったことから次の問いを作る → また調べる。端の話で相棒に質問はしない
- 見切り: 最低 2 回は掘り、そのあと糸の収穫 (減らせた不確実性の移動平均) が、ふだんの調べもの 1 回の平均 × 0.5 を下回ったらやめる。
  最適採餌の**限界値定理** (Charnov 1976) と**情報採餌理論** (Pirolli & Card 1999) による [観測事実: 文献。0.5 倍が最適かは未検証 → 進化で調整]
- 掘って知ったことは、ほかの知識と同じ規則で扱われる (確かめたことは価値に応じて口に出る)。**誰かと結びつけて考えたり、それで動いたりする仕組みは無い**

### 18.4 選択圧 (カーネルが測る)

**自発性** (`kernel/initiative.py`):
- 発話の口 (`say`) と入力の口 (感覚器の `poll`) にカーネルが記録を差し込む。思考のコードを経由しない
- 相棒の入力から 60 秒以内の発話は返事。それ以外は「自分から言ったこと」
- 自分から言ってから 10 分以内に、相棒が同じ話題で話しかけたか `/good` → 反応あり。`/bad` → うるさがられた
- 反応するかどうかは相棒にしか決められないので、タチコマには水増しできない
- 進化の目標「自発性」: 指標は反応ありの回数 / 時間。反応ありの割合が 0.2 以上落ちる・うるさがられることが倍増する変更は撤回される
  (うるさく話しかけて数を稼ぐ方向には進めない)

**先見** (`kernel/foresight.py`): 拾った情報 (周辺も含む) が、後で相棒自身の行動 (話しかけ・編集・端末・画面) に同じ話題として出てきたか。
出どころ・話題ごとの「後で役立った割合」が、興味の「後で役立ちそうか」になる。指標は拾ったときの興味と後の有用性の AUC。

### 18.5 変異の余地: プラグイン (`kernel/plugins.py`)

既存の関数の小さな手直しからは、「目の端で知ったことを覚えている誰かと結びつけ、相棒に伝える」のような新しい振る舞いは生まれにくい。
そこで自己進化の変異に、**新しいプラグインを書く**階層を加えた (目標「自発性」「先見」で使える)。

- 脳 (CPU の Qwen2.5-Coder) に渡すのは、目標の選択圧の説明・プラグインが使える基本動作の一覧・今あるプラグイン・観察
  (自分から言ったことと相棒の反応、出どころごとの後で役立った数) だけ。**何を書くべきかは渡さない**
- アイデアを 3 つ出させ、論文・ネットで見当たらないものほど高く評価して選ぶ (§13.4 の新しさ)
- プラグインは `on_event(api, event)` / `on_tick(api)` を持つ。使える基本動作:
  出来事を見る・仮説と知識を見る・記憶を引く・自分の興味を見る・仮説を立てる・注意を向ける・調べる (推論 1 回)・考える (推論 1 回)・
  検索する (ニュース・ネット・論文・作業フォルダ。読み取りのみ)・ニュースを見張る・相棒に伝えたいことを置く・自分用のメモ
- 推論は 1 tick に 1 回まで・会話中は使えない。言うかどうか・いつ言うかは本体の発話の規則が決める
- 安全: 静的検査 (import の許可リスト、`_` で始まる名前・open/getattr/type などの禁止、`import tachikoma.text` の形の禁止) と、
  実行時の絞った組み込み関数・import の許可リスト。見張りつきで動かし、2 秒で終わらなければ外す。例外が 5 回続いたら外す
  (例外は記録され「頑健さ」の進化の材料になる)
- 本番に入る前に、Docker の隔離環境 (ネットワーク無し・読み取り専用・CPU/RAM 上限) で全テストを通す。
  そこには実物のプラグインをいろいろな出来事で動かす確認 (`tests/test_plugins_live.py`) が含まれる。その後 12 時間の試用期間で、
  狙った指標が良くなったものだけが残る。自分で書いたプラグインも、以後の改良 (code の階層) の対象になる

### 18.6 検証と限界

- [観測事実] テスト: 出発点のタチコマは、テレビの停電の話を掘って知っても、「田中さんは札幌に住んでいる」と知っていても、結びつけて動かない。
  自発性の記録 (返事は数えない・同じ話題の反応だけが報酬・/bad はうるさがられた)。プラグインは狭い入口で新しい振る舞いを足せる・推論は 1 tick に 1 回・
  抜け道 (内部属性・getattr・open・os・`import tachikoma.text`) は検査と実行時の両方で拒否・止まったり例外を繰り返すプラグインは外される。
  進化がプラグインを書いて試用に入れ、撤回で消える。内部に触れるプラグインは静的検査で不採用
- [観測事実] 本物の Docker の隔離環境で: 健全なプラグインを入れた写しは全 133 件合格、止まるプラグイン (sleep) を入れた写しは不合格 (本番に入らない)
- [低確度仮説] **求める振る舞いが実際に育つかは保証できない**。育つには少なくとも (1) CPU の 7B のコード生成モデルが意味のある
  プラグインを書けること、(2) 相棒の反応が選択圧として十分な数だけ得られること (試用期間 12 時間で比べる。反応が少ないと差が測れない)、
  (3) 長い時間 (多数の世代) が要る。どの程度の期間で何が育つかは、実際に動かして観察するしかない
- 観察の方法: `/evolution` (何を試して何が残ったか)、`/discoveries` (ネットで見当たらないやり方で定着したもの)、`evolvable/plugins/` (育った振る舞いそのもの)

## 19. Android 版 — RAM 4GB の端末で、同じ心を動かす (`android/` / `tachikoma/android/`)

**要件**: モデルをもっと軽く・入力系はそのまま・出力は文字だけ・学習システムはそのまま。

### 19.1 どこを変え、どこを変えないか

思考のコード (agent・好奇心・深掘り・記憶・学習データの規則・較正・先見・自発性・プラグイン・自己進化) は PC 版と**同じ Python**。
端末で違うのは外界との境界だけで、`tachikoma/android/` (カーネル) に閉じ込めた。

| 境界 | PC 版 | Android 版 |
|---|---|---|
| 推論 | Ollama (GPU) | llama.cpp を JNI で (端末の CPU)。`tachikoma_llm.cpp` |
| 構造化出力 | Ollama の format (JSON スキーマ) | JSON スキーマ → GBNF 文法 (llama.cpp 公式の変換器を同梱)。文字列に長さの上限を入れて、小型モデルでも JSON が必ず閉じるように |
| 入力 | ファイル・端末・ウィンドウ・マイク (Whisper)・カメラ (OpenCV + Gemma の画像入力) | 文字・端末の音声認識 (端末内で認識できれば優先)・カメラ (ML Kit: 顔の有無・物の名前・日本語の文字)・ネット |
| 出力 | 声 (SAPI/VOICEVOX)・画面 | 文字だけ (チャット画面と通知) |
| 常駐 | コンソール / supervisor | 前面サービス (通知を出して、画面を閉じても考え続ける) |

### 19.2 モデルの選択 (RAM 4GB)

- [合理的推定] RAM 4GB の端末では、OS と他のアプリが 1.5〜2GB を使う。モデルに回せるのは 1〜1.5GB 程度
- 既定: **TinySwallow-1.5B-Instruct** (Sakana AI、Qwen2.5-1.5B を日本語で鍛えたもの)。公式の GGUF に Q4_K_M は無く、
  いちばん軽い Q5_K_M (約 1.1GB [推定]) を使う ([観測事実] CI で Hugging Face の一覧から選ばれたのは tinyswallow-1.5b-instruct-q5_k_m.gguf)。
  文脈 2048 の KV は約 60MB [合理的推定: 28 層 × KV 2 頭 × 128 次元 × f16 から計算]
- 軽量版: Qwen2.5-0.5B-Instruct Q4_K_M 約 0.4GB (速いが日本語の質は下がる)
- ファイル名は Hugging Face の API で一覧を取り、量子化の優先順位 (Q4_K_M → Q4_0 → Q5_K_M → Q8_0) で選ぶ
- 計算部は端末の CPU に合う版 (ARMv8.2 の dotprod・i8mm など) を実行時に選ぶ (`GGML_CPU_ALL_VARIANTS`。llama.cpp 公式の Android 例と同じ設定)

### 19.3 学習システム

| 学習 | 端末でできること |
|---|---|
| 学習データ (やり取り・自律調査で確定した知識・判定、自分の出力を混ぜない規則) | そのまま (同じ dataset.py) |
| 即効層 (過去の確かな例を few-shot で添える)・確信の較正・先見・自発性 | そのまま |
| 自己進化 | パラメータの調整 (範囲はカーネルの bounds.json)。コードを書く CPU の脳 (7B) と Docker の隔離テストは端末に載らない。PC で育ったプラグインは純 Python なのでそのまま動く |
| 重み (LoRA) の学習 | 計算は PC。端末は学習データを zip で書き出し → PC の `finetune/android_adapter.py` が同じ基盤モデルで LoRA を学習して GGUF にする → 端末が取り込み、PC 版の Learner と**同じ採否の規則** (健全性検査 + 検証標本の採点で現行より悪くないこと) で採用・不採用を決める |
| 耳 (Whisper)・目 (OCR) の学習 | 端末ではしない (端末の音声認識と ML Kit は学習できない) |

[合理的推定] RAM 4GB の端末では、PyTorch も、1.5B モデルの学習に要る勾配・最適化器の状態も載らない。だから「学習の計算」だけを PC に預け、
「何を学ぶか」「採用するか」は端末で PC 版と同じ規則で決める。

### 19.4 端末の制約への対処

- 相棒が話しかけたら、走っている背景の推論 (評価・深掘り) を打ち切って返事を優先する。返事の推論は打ち切らない
- 電池が 30% 未満で充電していないときは、自分からは考えない (話しかけには答える)。背景思考が CPU を使う割合は 3 割まで
- 入力が文脈 (2048) に収まらなければ、中ほどを省く (前は状況、後ろは新しい出来事なので残す)
- 返事の前の点検 (知らないこと・怪しい前提の洗い出し) は、推論 1 回ぶん遅くなるので既定で切る (config で戻せる)
- 同梱のタチコマ本体は、初回に書き込める場所 (files/home) へ展開する。アプリを更新しても、自己進化で書き換わったファイルは残す (Windows 版と同じ規則)

### 19.5 検証と限界

- [観測事実] 推論層の C++ (JNI) は、同じ版の llama.cpp をこの開発環境で組んで、Java の試験台から確かめた:
  読み込み・文法なしの生成・JSON スキーマの文法どおりの生成 (判定・評価のスキーマで、何度やっても正しい JSON)・壊れた文法の拒否・
  長すぎる入力の拒否・アダプタの着脱・打ち切り・解放後の拒否
- [観測事実] Python 側 (推論の窓口・入力の振り分け・カメラの調べ方・学習データの書き出し・アダプタの採否・起動と更新) は、偽の端末と偽の推論でテスト
- [観測事実] GitHub Actions で APK を組み、エミュレータ (x86_64・RAM 4GB) に小型の実モデル (Qwen2.5-0.5B) を置いて、起動 → 話しかけ → 返事、まで確かめる
- 未確認: 実機 (arm64) での速さ・発熱・電池の減り、端末ごとの音声認識の違い、TinySwallow での応答の質
- [低確度仮説] 1.5B のモデルは、Gemma 4 E2B より評価・判定の質が落ちる。好奇心や深掘りの「問い」の質が下がる分は、
  先見と自己進化 (パラメータ) がどこまで補えるか、実機で観察が要る

## 20. 外への関所 — 情報は取りに行く、でも個人の情報は出さない (`kernel/egress.py`)

相棒の要求: 「ローカル環境から外部に発信できるのは、個人情報を持たないテキストデータのみ。画像について興味をもっても
画像で検索せず、言語化して検索させたい。情報を取りに行かせたいが、プライバシーも両立したい」

### 20.1 どこで止めるか

- 比べた案:
  - A. 検索する側 (web.py・scholar.py・news.py) で、それぞれ検索語を消毒する
  - B. 通信そのもの (urllib の `OpenerDirector.open`) を差し替え、すべての通信を一か所で調べる
- 採ったのは B (A の消毒も、B と同じ規則を呼ぶ形で残す)。理由:
  - [合理的推定] A だけだと、新しい取得口 (自己進化で増えたプローブ・プラグイン・将来のセンサー) が消毒を忘れると漏れる
  - B なら「外へ出る道は一つ」で、その規則はカーネルにあり、思考のコードからは変えられない
- 思考のコードは urllib・http・socket を import できない (以前から)。今回、ほかのモジュールを経由して届く道
  (`web.urllib…`・`web.egress…`・`OpenerDirector`・`HTTPSConnection`) も静的検査で閉じた
- 同じ PC の中 (loopback) と、config に IP アドレスで書いた家の中の機械は外ではないので通す (本文つきの送信も)

### 20.2 何を出してよいか

1. 形: 外へは GET/HEAD だけ。本文・Cookie・Authorization・URL の中の利用者名があれば止める。
   → 画像・音声・ファイル・記憶は、どう頑張っても外に出る形を持たない
2. 中身: 問い合わせの値を調べる
   - 止める: メール・電話・郵便番号・番地までの住所・6 桁以上の番号・カード型の番号・IP・ファイルの場所・トークン・base64・生年月日
   - 取り除く (clean): 敬称つきの名前・Mr./Dr. つきの名前・相棒や PC の名前・覚えた名前・相棒や身近な人を指す語。
     「私の妻 糖尿病 治療」は「糖尿病 治療」になって出ていく。取り除くと問いが残らなければ出さない
   - 公開文献の番号の問い返し (PubMed の `id=` に番号の並びだけ) は、相手が返した番号なので止めない
3. 名前の覚え方: 相棒の側から入ってきた文字 (話しかけ・声・ファイル・作業画面・カメラの説明) に「〇〇さん」の形で出てきた名前を
   `privacy_terms` に覚える (「みんなさん」「お客さん」は覚えない)。ニュースに出てきた名前は覚えない
   (ニュースの人物を調べるのは、相棒の個人情報ではない)。`/private`・`/public` で相棒が足し引きできる
4. 記録: 外に出したもの・止めたものを `egress.log` に 1 行ずつ残す。`/egress` で見られる

### 20.3 画像への興味

- 画像を外に送る道はない (20.2 の 1)。カメラ・画面は、この PC の中のモデルが文章にしてから記憶に入る (以前から)
- 検索の計画 (PLAN_SYSTEM) に「見たものを一般的な言葉に言い換えて検索語にする。人の見た目・顔・名前は入れない」を足した
- [合理的推定] 言い換えの質は、深掘りで得たもの (先見の帳簿) を通じて自己進化の選択圧がかかる

### 20.4 限界

- [観測事実] 関所は urllib を通る通信を見る。モデルの初回ダウンロード (Ollama は別プロセス・Whisper は huggingface_hub) と
  yt-dlp (別プロセス) は関所の外。どれも公開ファイルを取るだけ。huggingface_hub の利用状況の送信は環境変数で切る
- [合理的推定] 規則で見つけられない個人情報 (敬称なしの珍しい名前・遠回しな言い方) はありうる。気づいたら `/private` で教える。
  `egress.log` を見れば、何が出ていったかは後から必ず確かめられる
- [観測事実] Android 版も同じ関所を通る。ただし端末に端末内の音声認識が無い (Android 11 以前など) と、
  OS の音声認識が音声を外で処理する場合がある (アプリの外の仕組み)

## 21. 完全アンインストール — 入れる前の姿に戻す (`packaging/footprint.py` / `packaging/uninstaller.py`)

相棒の要求: 「.exe 実行後の完全アンインストールツールも作ってくれ。原状回復しやすいように」

### 21.1 何を「元の姿」とするか

- 比べた案:
  - A. 知っている場所を全部消す (インストール先・Ollama の gemma・Hugging Face のキャッシュ…)
  - B. 入れる前の姿を記録しておき、差分 (タチコマが持ち込んだもの) だけを消す
- 採ったのは B。理由:
  - [合理的推定] A は、相棒が前から使っていた Ollama のモデルや Hugging Face のキャッシュまで消してしまう。
    それは「原状回復」ではなく「別の破壊」
  - B なら「前からあったものは残す」が台帳で言える。台帳が無い・当てにならない (古い版から更新して、入れた後で写した) ときは、
    分からないものとして尋ねる (--yes では消さない、--all で消す)
- さらに、そもそも外に散らからないようにした: pip・Hugging Face・PyTorch のキャッシュと Hugging Face のログイン情報を
  インストール先の中に置く (`cache_env`)。散らからなければ、戻す作業も要らない

### 21.2 何が PC に残りうるか (洗い出し)

| 場所 | 誰が作る | 取り除き方 |
|---|---|---|
| `%LOCALAPPDATA%\Tachikoma` (記憶・設定・Python・進化・キャッシュ) | 入口 | 消す (動いていれば先に止める) |
| スタートメニュー `Tachikoma.lnk` | 入口 | 消す |
| `HKCU\…\Uninstall\Tachikoma` (「設定 → アプリ」) | 入口 | 消す |
| Ollama のモデル `gemma4:e2b` | 入口 (取得) | 台帳に「取った」とあれば消す。前からあったら残す |
| Ollama のモデル `tachikoma-vN` | 頭の学習 | 必ず消す (タチコマにしか作れない名前) |
| Docker のコンテナ `tachikoma-cpu-brain`・イメージ | 自己進化 | コンテナは消す。イメージは前に無かったら消す |
| Hugging Face・pip のキャッシュ (利用者の場所) | 古い版 | 前に無かったら消す。分からなければ尋ねる |
| マイク・カメラの許可の記録・MuiCache・互換性の記録 | Windows | インストール先・起動した exe の場所を指すものだけ消す |
| ファイアウォールの規則 | Windows (許可したとき) | インストール先の Python を指すものだけ消す |
| `%TEMP%` の声の一時ファイル・展開の残り (`_MEI*`) | 本体・PyInstaller | 消す |
| Ollama 本体・`.ollama` | 相棒 (案内に従って) | 前に無かったなら尋ねる (`--remove-ollama`)。`.ollama` は前に無かったときだけ |
| Docker Desktop | 相棒 | 自動では消さない (WSL と結びついた大きな仕組み)。案内だけ |

### 21.3 自分自身を消す

- 「設定 → アプリ」から呼ぶと、インストール先の `Tachikoma.exe --uninstall` が動く。Windows は動いている exe を消せないので、
  自分を一時フォルダに写してそちらで続け (新しいコンソール)、最後に写しも少し後で消す (`cmd /c ping … & del`)
- 最後に候補を一つずつ調べ直して「済み / 残っている」を出す。残っていれば (使用中のファイルなど) 再起動後にもう一度、と案内する

### 21.4 検証と限界

- [観測事実] 偽の PC (利用者のフォルダ・Ollama・レジストリ) の上で、入れる → 使う → 取り除く、を通すテスト:
  前からあった Ollama のモデル・Hugging Face のキャッシュ・ほかのアプリの記録は残り、タチコマのものだけが消える。
  台帳が無いときは確かなものだけ消え、尋ねて「はい」なら残りも消える。見るだけ (--dry-run) は何も変えない
- [観測事実] GitHub Actions の Windows で、実際に入れて (スタートメニュー・アプリ一覧の登録まで) から、
  インストール先の `Tachikoma.exe --uninstall --yes` (自分を写して続ける道) と `TachikomaUninstall.exe` の両方で取り除き、
  インストール先・スタートメニュー・レジストリ・一時フォルダの写しが残っていないことを確かめる
- [合理的推定] 台帳より前 (この版より前) に入れた場合、入れる前の姿は分からない。そのときは消すかどうかを尋ねる
- 範囲外: ブラウザの履歴 (http://127.0.0.1:8765 を開いた記録)、Windows のプリフェッチ・イベントログなど OS が自動で持つ記録。
  これらは個人のデータを含まず、OS が自分で古いものから捨てる
