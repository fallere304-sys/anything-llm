# DualMicTranscriber — 2マイク音量比較による 2話者分離文字起こし（概念実証）

同じ部屋で話す2人の会話を、**2本のマイクで同時録音**し、
**マイク間の音量差**で話者を識別したうえで、**Whisper** で文字起こしし、
**ローカルLLM** で話者付き文字起こしの補正版を作る Windows アプリです。
すべての処理はノートPCの CPU とメモリ（RAM 16GB を想定）で完結し、録音データを外部へ送信しません。

```
 マイク1(話者A側) ─┐                       ┌─ Whisper ─ 話者付与 ─┐
                   ├─ 同時録音 ─ 時刻合わせ ┤                      ├─ 規則統合 ─ ローカルLLM補正 ─ 完成版
 マイク2(話者B側) ─┘        │              └─ Whisper ─ 話者付与 ─┘
                            └─ 音量比較 → 話者タイムライン（録音開始からの秒）
```

---

## 1. 使い方

### 1.1 exe の入手

| 方法 | 手順 |
|---|---|
| GitHub Actions（推奨） | このディレクトリに変更を push すると `.github/workflows/dual-mic-transcriber.yml` が Windows 上で exe をビルドし、Artifacts に `DualMicTranscriber-windows-x64` として添付します（Actions タブから手動実行も可） |
| 手元でビルド | Windows に Python 3.11 を入れ、`build.bat` をダブルクリック → `dist\DualMicTranscriber.exe` |

### 1.2 起動（＝環境構築）

`DualMicTranscriber.exe` をダブルクリックするだけです。Python 等のインストールは不要です。

- 実行に必要なライブラリ（Whisper 推論エンジン、llama.cpp、音声入出力）はすべて exe に同梱されています。
- **初回起動時のみ**、モデルを自動ダウンロードします（インターネット接続が必要）。
  起動直後からバックグラウンドで始まり、スタート画面下部に進捗が出ます。録音はダウンロード中でも可能です。

| モデル | 既定 | 容量の目安 | 保存先 |
|---|---|---|---|
| Whisper（文字起こし） | `medium`（CTranslate2 / int8 で実行） | 約1.5GB | `%LOCALAPPDATA%\DualMicTranscriber\models` |
| ローカルLLM（補正） | `Qwen2.5-3B-Instruct` Q4_K_M（GGUF） | 約2GB | 同上 |

2回目以降はオフラインで動作します。

> [!NOTE]
> 署名なしの exe のため、初回に Windows SmartScreen の「WindowsによってPCが保護されました」が出ることがあります（「詳細情報」→「実行」）。
> PyInstaller の単一 exe は展開に時間がかかるため、起動に10〜30秒程度かかることがあります。

### 1.3 画面の流れ

1. **スタート画面**: 横並びの2つのドロップダウンで、マイク1（話者A側）・マイク2（話者B側）を選択 → 「● 録音開始」。
   録音中は「■ 停止」ボタンに切り替わり、各マイクの入力レベルメーターと経過時間が表示されます。
   *話者Aが話したときにマイク1のメーターが大きく振れる* 配置になっていることを確認してください。
2. **処理画面**: 停止すると自動で遷移。9つの処理フェーズの進行状況（✔ 完了 / ▶ 実行中）、現在の処理内容、進捗バー、「処理停止」ボタン。
3. **結果画面**: タブで次を表示（すべて編集・選択・コピー可能。`Ctrl+A` で全選択）。
   - 完成版（AI補正）
   - 規則ベース統合（AIを通す前の下書き）
   - マイク1 話者付き / マイク2 話者付き
   - 話者タイムライン

   「表示中のタブを全てコピー」「保存フォルダを開く」、下部に「スタートに戻る」。

### 1.4 マイクの置き方（精度に直結）

- 各マイクは担当話者の口元から **30cm 以内**、相手からはできるだけ遠くに置く。2本のマイク間は 1m 以上離すのが望ましい。
- 指向性マイク（単一指向性ピンマイク等）を担当話者に向けると、音量差が大きくなり識別精度が上がる。
- 「同じ物理マイクの別ドライバ」（例: 同名の WASAPI 版と MME 版）を2つ選ぶと意味がありません（同名の場合は警告が出ます）。

## 2. 設計思想

### 2.1 基本方針

| 方針 | 理由 |
|---|---|
| **物理的な手がかり（距離による音量差）を一次情報にする** | 1本のマイクの音声から声質で話者を推定する方式（pyannote 等の話者埋め込み）は、PyTorch が必要で重く、短い相槌・似た声質に弱い。2本のマイクがあれば「どちらのマイクに近いか」という、より単純で頑健な手がかりが使える。 |
| **2本とも文字起こしし、「近い方のマイク」の結果を優先する** | 話者Aの発言はマイク1で高 SNR に録れているので、マイク1の認識結果の方が正確。逆も同様。両方を残すことで、片方の誤認識・取りこぼしをもう片方で補える。 |
| **LLM は「生成」ではなく「照合・校正」に使う** | 小型ローカルLLMに白紙から整形させると要約・創作が混ざる。規則ベースの下書き＋2本の生認識結果を与え、照合して直す作業に限定する。LLM が失敗しても下書きを結果として出す（フォールバック）。 |
| **重い処理は逐次実行し、メモリを使い回す** | Whisper の処理が終わったらモデルを解放してから LLM を読み込む。ピークメモリを 16GB ノートで安全な範囲（数GB）に抑える。 |
| **処理速度より「止まらないこと」** | 概念実証の要件に合わせ、すべてワーカースレッドで実行し、UI は 100ms ごとのポーリングで更新する。停止要求はセグメント／トークン単位で確認する。 |
| **ダブルクリック1回で完結** | 依存ライブラリは PyInstaller で単一 exe に同梱し、モデル（数GB、ライセンス上も同梱より DL が適切）は初回起動時に自動取得する。 |

### 2.2 技術選定で比較した選択肢

| 論点 | 採用 | 比較した代替案 | 採用理由 |
|---|---|---|---|
| 実装言語・UI | Python + Tkinter | C#/.NET (WPF) + whisper.cpp | Whisper・LLM の CPU 推論ライブラリが Python で最も成熟。Tkinter は標準ライブラリで追加依存なし。 |
| Whisper 実行系 | faster-whisper（CTranslate2, int8） | openai-whisper（PyTorch）、whisper.cpp | PyTorch 不要で exe が小さく、CPU int8 で高速・省メモリ。単語タイムスタンプと VAD を内蔵。 |
| LLM 実行系 | llama-cpp-python（llama.cpp, GGUF） | Ollama、transformers | Ollama は別途インストールが必要で「exe 1つ」の要件に反する。transformers は PyTorch が必要で重い。llama.cpp は CPU 量子化推論が最も軽量。 |
| 話者識別 | 2マイクのフレーム音量差（SNR 差） | 話者埋め込みクラスタリング、到達時間差（TDOA） | 要件で指定された方式。TDOA は2台の別デバイスではサンプル単位の同期が取れず不安定。 |
| 配布形態 | PyInstaller `--onefile --windowed` | インストーラ、埋め込み Python を初回 DL | 単一 exe のダブルクリックという要件に最も直接的。 |

## 3. 処理方法（要件の処理案①〜⑥との対応）

### ① 2本のマイクで同時録音 — `app/recorder.py`

- 2つの入力デバイスをそれぞれ独立した PortAudio ストリームで開く（デバイスごとに既定のサンプリングレートで録音。開けない場合はレート・チャンネル数を変えて再試行）。
- 音声コールバックで受けたブロックはキューで書き込みスレッドへ渡し、`mic1.wav` / `mic2.wav`（16bit mono）に逐次書き出す。長時間録音でもメモリを消費しない。
- 各ストリームの **最初のサンプルの取り込み時刻** を共通の高精度時計（`time.perf_counter`）で記録しておく。

### ② 音量比較による話者区別 — `app/diarize.py`

1. 両 WAV を 16kHz mono に変換（`soxr` で高品質リサンプリング）。
2. **時刻合わせ**: 遅く始まった方の開始時刻を時間軸の 0 とし、早く始まった方の先頭を削る。終端は短い方に合わせる。
3. 50ms ごとのフレームで RMS 音量（dBFS）を計算。
4. **入力差の補正 第1段（雑音下限基準）**: 各マイクの「雑音下限」（全フレームの下位10%点）を引き、雑音下限からの持ち上がり量 `SNRᵢ = dBᵢ − floorᵢ` を求める。
   マイクの感度（ゲイン）・Windows の入力音量設定は信号にも雑音にも等しく掛かるため、dB の差を取ると打ち消される。
5. 差 `d = SNR₁ − SNR₂` を 400ms の移動平均で平滑化。
6. **入力差の補正 第2段（自動バランス）**: 第1段は「2本のマイクの周囲雑音が同程度」という前提に立つため、片方だけ PC のファンやエアコンの近くにあると雑音下限が高くなり、そちら側の話者が常に小さく判定される（合成データで、雑音下限が14dB違うと正解率が0.48まで落ちることを確認）。
   そこで、発話中フレームの `d` の分布を2クラスタに分け（1次元 k-means）、**「A発話の山」と「B発話の山」の中点が 0 になるよう `d` 全体をずらす**。中点は2人の発話量の比に依存しないので、片方がほとんど話す会話でも成立する。
   - 安全装置: 1人しか話していない録音でも、声の大小で分布が2つに割れることがある。そこで「上の山ではマイク1自身の SNR が、下の山ではマイク2自身の SNR がそれぞれ 1.5dB 以上高い」という物理的整合性を確認し、満たさなければ第2段は適用しない（第1段のみ）。1人だけの場合、相手側マイクには回り込み音しか入らないため、この条件は満たされない。
   - 補正量と判断理由は `speaker_timeline.json` の `balance_offset_db` / `balance_note` と、結果画面の「話者タイムライン」タブ先頭に表示される。
7. 判定（フレームごと）:
   - `max(SNR₁, SNR₂) ≤ 8dB` → 無音
   - `d > +3dB` → 話者A ／ `d < −3dB` → 話者B ／ それ以外 → 判別不能（`?`、同時発話など）
8. 300ms 未満の短い話者区間は、隣接する長い区間のラベルに吸収（ちらつき除去）。

### ③ 話者区別情報を録音開始からの時間で記録

`speaker_timeline.json` / `.csv` に `start_sec, end_sec, speaker` の形で保存（時刻は時刻合わせ後の録音開始からの秒）。

### ④ Whisper で2本とも文字起こし — `app/transcribe.py`

- faster-whisper（CPU / int8）で **マイク1・マイク2 の両方** を全区間文字起こし。
- `word_timestamps=True`（単語ごとの時刻）、`vad_filter=True`（無音区間を飛ばし幻覚を抑制）、`condition_on_previous_text=False`（長時間での繰り返し幻覚を抑制）。

### ⑤ 文字起こしへの話者識別付与 — `app/merge.py`

- 2本の文字起こしの **それぞれ** について、各単語の時間区間に含まれるフレームの話者ラベルを多数決し、話者を付与する（拮抗時は音量差の平均の符号で決定）。
- 同じ話者の連続する単語（間隔1秒未満）を1発話にまとめる。単語単位で判定するため、Whisper の1セグメント内で話者が交代しても分割できる。
- さらに **規則ベース統合版（下書き）** を作る: 話者Aの発言はマイク1、話者Bの発言はマイク2 の認識結果を採用し、採用側でカバーされていない時間帯の発言だけを反対側のマイクから補う。

### ⑥ ローカルLLMによる補正版の作成 — `app/llm.py`

- 120秒ごとの時間窓に区切り（コンテキスト長対策）、各窓について「下書き」「マイク1話者付き」「マイク2話者付き」の3資料を LLM に与え、照合・補正した1本の文字起こしを `[mm:ss.s] 話者X: 発言` 形式で出力させる。
- プロンプトで「要約・追加の禁止」「話者ラベルは文脈上明らかな誤りのみ修正」「本文以外を出力しない」を指示。出力から形式に合う行のみを抽出する。
- 窓ごとに失敗・空出力なら、その窓は下書きで代替する（警告を結果画面に表示）。

## 4. 出力ファイル

| ファイル | 内容 |

## 5. 設定（config.json）

初回起動時に `%LOCALAPPDATA%\DualMicTranscriber\config.json` が既定値で作られます。編集後、アプリを再起動すると反映されます。

| キー | 既定値 | 説明 |
|---|---|---|
| `language` | `"ja"` | 認識言語。`""` で自動判定 |
| `whisper_model` | `"medium"` | `small`（速い・低精度）〜 `large-v3`（遅い・高精度、RAM 約3〜4GB） |
| `whisper_compute_type` | `"int8"` | CPU 向け量子化。失敗時は自動で `float32` に切替 |
| `llm_repo` / `llm_file` | Qwen2.5-3B-Instruct Q4_K_M | Hugging Face 上の GGUF。品質を上げるなら 7B 級の単一ファイル GGUF を指定（RAM 約6GB、処理時間は2倍以上） |
| `llm_chunk_seconds` | `120` | LLM に一度に渡す時間幅 |
| `vad_threshold_db` | `8.0` | 雑音下限からこの dB を超えたら発話 |
| `dominance_margin_db` | `3.0` | 2マイクの SNR 差がこれ未満なら判別不能 |
| `auto_balance` | `true` | 入力差の補正 第2段（自動バランス）を使う |
| `smoothing_ms` / `min_segment_ms` | `400` / `300` | 音量差の平滑化幅 / 最短話者区間 |
| `threads` | `0` | CPU スレッド数（0 = 論理コア数−1） |

## 6. リソース見積り（RAM 16GB ノートPC）

| 項目 | 目安 | 根拠 |
|---|---|---|
| Whisper medium（int8） | 約1〜2GB | [合理的推定] CTranslate2 int8 の重み約0.8GB＋作業領域 |
| LLM 3B Q4_K_M | 約2.5GB | [合理的推定] 重み約2GB＋KVキャッシュ（8192トークンで約0.3GB） |
| 音声データ | 1時間あたり約0.5GB | [観測事実] 16kHz float32 × 2本 = 230MB × 2 |
| **ピーク** | **約3〜4GB** | Whisper と LLM は同時にメモリに載せない |

処理時間は CPU 性能に強く依存します。[合理的推定] 4〜8コアのノートPCで、Whisper medium は1本あたり録音時間の0.5〜2倍程度、LLM 補正は1時間の会話で30分〜1時間程度。

## 7. 制約・既知の限界

| 項目 | 内容 |
|---|---|
| 2デバイス間のクロック差 | 別々の USB/Bluetooth デバイスは水晶発振器が独立しており、長時間録音で数十ms〜数百msずれる。開始時刻は合わせるが、ドリフトは補正しない（1秒以上ずれた場合は警告）。[合理的推定] 1時間で50〜200ms程度なら50msフレーム・400ms平滑化の判定にはほぼ影響しない。 |
| 開始時刻の精度 | コールバック到着時刻から推定するため、[合理的推定] 数十ms 程度の誤差がありうる。 |
| 反響の強い部屋・マイクが近すぎる配置 | 2本の音量差が小さくなり、`?`（判別不能）や誤判定が増える。合成データでは 3dB 程度の差まで正しく分離できたが [観測事実: tests/test_logic.py 相当の合成信号]、実環境の反響・雑音下での精度は未検証。 |
| 入力差の自動補正の限界 | 自動バランスは「録音全体で一定のずれ」を補正する。Windows の「マイクの自動音量調整（AGC）」や「音声の強調」が有効だと、ゲインが時々刻々変わり補正できないため、サウンド設定で無効化を推奨。また、回り込みが強く（相手の声が −3dB 程度でしか減衰しない）かつ片側の雑音が大きい配置では、2話者の山を確認できず第1段のみになる（合成データで確認）。 |
| 同時発話（オーバーラップ） | 1フレームに1話者しか割り当てないため、大きい方の話者に寄せられる。 |
| Bluetooth ヘッドセット | ハンズフリープロファイルに切り替わり音質が低下（8〜16kHz）、遅延も大きい。有線/USB マイク推奨。 |
| 停止ボタンの反応 | モデル読込・ダウンロード中など、ライブラリ内部の処理中は区切りまで待ってから停止する。 |
| CPU 要件 | llama.cpp は AVX2 対応 CPU を前提にビルド（[合理的推定] 2015年以降の一般的なノートPCは対応）。 |
| ウイルス対策ソフト | PyInstaller 製の単一 exe は誤検知されることがある。 |

```bat
python -m pytest -q tests
```

- `tests/test_logic.py`: 合成した2話者・2マイク信号（マイク感度差 18dB、クロストーク −10dB）で、話者識別・時刻合わせ・話者付与・統合を検証。入力差補正については、片側だけ雑音が大きい（雑音下限 +14〜20dB）、発話量の偏り（85% vs 15%）、1人だけ話す（補正が誤作動しないこと）の各ケースを検証。
- `tests/test_pipeline.py`: 44.1kHz と 16kHz・開始 0.3 秒ずれの2本の WAV から、Whisper/LLM をモックにしてパイプライン全体（フェーズ順・出力ファイル・LLM 失敗時のフォールバック・停止）を検証。

### 開発時の実行

```bat
pip install -r requirements.txt
python run.py
```

### ビルドの注意

- `llama-cpp-python` は PyPI に Windows 用ホイールが無いため、`build.bat` は CPU 用ホイール配布サイトを優先し、無ければソースビルドする（Visual Studio Build Tools の C++ と CMake が必要。GitHub Actions の `windows-latest` には同梱済み）。
- ソースビルド時は `-DGGML_NATIVE=OFF` でビルドマシン固有の CPU 命令を使わないようにしている（配布先 PC での異常終了防止）。
- CI ではビルド後に `DualMicTranscriber.exe --selftest` を実行し、同梱ライブラリ（PortAudio, soxr, onnxruntime/VAD, CTranslate2, llama.cpp, Tk）が exe 内から読み込めることを確認する。
