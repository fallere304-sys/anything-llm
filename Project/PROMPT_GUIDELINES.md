# PROMPT_GUIDELINES.md — GPT-OSS-120B向けタスク分割・プロンプト設計方針

版: v0.1 / 2026-11-18。**ユーザーのローカル環境（実行基盤・コンテキスト長・最大出力長）が未確認**のため、数値は仮置き。確認後に更新する。

## 1. 前提 [合理的推定／要確認]
- GPT-OSS-120Bはコードを**実行・ビルドできない**。出力は未検証のテキストである。
- 学習データの偏りから、**英語の指示のほうが日本語より安定する**可能性が高い。コード・識別子・指示文は英語、テストデータ・UI文言・エラー文言は日本語リテラルとする。各プロンプトの冒頭に、ユーザー向けの日本語1〜2行の要約を付ける（GPTには不要だが、ユーザーが内容を判別するため）。
- 長い出力や多ファイル同時生成では、切り詰め・不整合・APIの取り違えが増える。
- **確定(2026-11-18)**: 実行基盤は **llama.cpp**。
- **未確認**: 起動オプションの `-c`（コンテキスト長）、`-n`（最大生成トークン）、reasoning effortの設定、量子化・GPU/RAM構成。
- llama.cpp利用に関する注意 [合理的推定: 版数により異なるため要確認]:
  - GPT-OSSは推論過程(reasoning)のトークンも生成するため、**コンテキスト長は「プロンプト＋推論＋出力コード」の合計**で消費される。プロンプトは短く保ち、出力を長くしすぎない（上記の分割原則が必須）。
  - 出力がコードの途中で切れる事故を避けるため、`-n` を十分大きく（または無制限）設定する。切れた場合は検品でFAIL(truncated)とし、分割して再依頼する。
  - reasoning effort は、llama-server のチャットテンプレート引数で指定できる場合がある。コード生成では **medium〜high** を推奨（要検証）。
  - サンプリングは、出力が不安定な場合は低temperature（例 0.2〜0.6）を推奨（要検証）。

## 2. 分割の原則
1. **1プロンプト = 1ファイル、または密結合な数ファイル**（出力の目安 150〜400行）。出力が長くなる見込みなら分割する。
2. **インターフェースを先に凍結**（INTERFACE_SPEC.md：型・関数シグネチャ・JSONスキーマ）。各プロンプトは必要な部分を**全文コピーして埋め込む**（他のプロンプト・文書の参照に頼らない）。重複は意図的。
3. **依存の浅い順に**: データ型 → 純粋関数のルール（入出力が明確で最も任せやすい）→ 解析器(CSVパーサ・文字コード) → 結果集計 → 出力(CSV/Excel/HTML) → ルールJSONの読込・検証 → CLI(ヘッドレス) → GUI → テスト・CI。
4. **純粋ロジックを厚く、GUIを薄く**（GUIは検証が最も難しい。ロジックはLinuxでテスト可能）。
5. **各ルール(E001〜E017)は独立の関数/モジュール**にし、1プロンプトに複数ルールをまとめても1ルール1テーブルで記述（小さく確実に）。
6. 相互依存が強い箇所を無理に細分化しない（例: パーサの状態機械は1プロンプト）。

## 3. プロンプトの構造（固定テンプレート）
```
[日本語要約 1-2行（ユーザー向け）]
=== TASK ID / CONCEPT ===
=== GOAL (what to implement now) ===
=== NOT IN SCOPE (do NOT implement) ===
=== ENVIRONMENT & PINNED DEPENDENCIES (exact versions; use ONLY these; stdlib otherwise) ===
=== CONTRACT (types / signatures / JSON schema, verbatim) ===
=== BEHAVIOR SPEC (rules, edge cases, semantics) ===
=== EXAMPLES (input → expected output table; at least N cases incl. edge cases) ===
=== ERROR HANDLING & SECURITY REQUIREMENTS ===
=== DEPENDENCIES ON OTHER MODULES (only the interfaces, inlined) ===
=== DEFINITION OF DONE (checklist) ===
=== PROHIBITIONS ===
=== OUTPUT FORMAT (exact) ===
```
これで要求仕様の17項目をすべて満たす。

## 4. 精度を上げるための具体策
- **例(入出力テーブル)を多く**: 仕様の文章よりも、具体的な入力→期待出力のほうがモデルに伝わりやすい。エッジケースを必ず含める。
- **依存はバージョン固定、使用APIを限定**。「不確かなAPIは使わず標準機能で書け。不確かな点は 'UNCERTAIN:' と明記」を指示（ハルシネーション抑制と検品効率化）。
- **同時にテストを書かせる**（プロンプトの例をそのままテストケース化）。Claudeがそのテストを実行して検品する。
- **自己チェックを書かせる**: 出力前に完了条件チェックリストを1つずつ確認し、末尾に「確認結果」を記載（ただし自己申告は採用せず、Claudeが実行確認する）。
- **禁止事項を明示**: 省略（`...` や `// rest unchanged`）、疑似コード、TODO放置、未指定ライブラリの追加、ネットワーク使用、`eval`/動的コード実行、ファイルへの書込（検査コア）。
- **出力形式を厳密に**: 各ファイルを `### FILE: <相対パス>` 見出し＋コードブロック1つで完全出力。続けて `### NOTES`（使い方・依存・未実装・既知の問題・UNCERTAIN項目）。
- **再提出プロンプトは差分指示＋該当コード全文再掲**: 問題箇所・原因・修正内容・維持すべき仕様・完了条件を明示し、完全なファイルを再提出させる。
- 1回の入力にコーパスやexpected.json(hold-out)を含めない。

## 5. 技術選定の観点（PHASE 2で各案に適用）
GPT-OSSが**確実に書ける**（学習量が多く、APIが安定している）スタックを優先する。新しい/マイナーなFWはAPIの取り違えが増えるため、採用時は使用APIを最小限に絞って明示する。GUIは特に危険なので、「GUI層は小さく、ロジック層は大きく」を各案の設計制約にする。

## 6. 検品フロー（Claudeの作業）
受領 → ファイルを所定位置へ配置 → 構文・静的解析 → 単体テスト(Linux)実行 → 契約適合確認 → レビュー（セキュリティ/例外/保守性）→ PASS / CONDITIONAL PASS / FAIL 判定 → FAIL時は§4の再提出プロンプトを作成。Windows固有部分はCI(Actions)で確認。

## 7. 共通評価基盤のタスク（E系。GPT-OSSが実装）
E-001 合成CSV生成器（シード固定・不正注入・expected.json出力）／E-002 エッジ・異常入力ファイル生成／E-003 採点器（precision/recall/F1・突合キー）／E-004 `findings.json` スキーマ検証／E-005 性能計測ランナー／E-006 CI workflow(Windows)。Claudeは仕様とプロンプトを作り、検品する。
