# CONCEPTS.md — 4つのコンセプト（PHASE 2）

版: v0.1 / 2026-11-18。全案は REQUIREMENTS の MUST と INTERFACE_SPEC v1.0 を満たす。違いは**問題の解き方**。

## 0. 技術選定の共通判断基準
1. GPT-OSS-120Bが**確実に書ける**（学習データが豊富でAPIが安定）。**GPTの知識が及ぶ過去の安定版にバージョンを固定**する（最新版はAPI取り違えの原因になる）。
2. コンテナで**検査コアをテスト可能**（Go/Rust/Node/Python導入済み [観測事実]）。
3. Windows CI(windows-latest)でビルド可能（前提 [未確認: U-4]）。
4. 「GUI層は薄く、ロジック層は厚く」を全案の設計制約とする。

## 2. 各案が検証する「仮説」（アリーナで勝敗以外にも学ぶ点）
- A: 単純さは精度・安全性で勝てるか。ローカルHTTPサーバ方式のセキュリティ（Hostヘッダ検証・トークン）は十分か。
- B: プラグイン/DSLの抽象化コストは、拡張性の得点に見合うか。
- C: 優先度最下位の速度に特化した設計は、精度・安定性を損なわないか。
- D: 自動ルール提案は、誤提案なく業務担当者の負担を減らせるか。

## 3. 独立性の担保
- 各案は `/Project/{A,B,C,D}/` に閉じ、他案のコード・設計書を参照しない。
- 共有するのは **INTERFACE_SPEC.md（契約）と `/Project/eval/`（評価基盤）のみ**。
- 4案の**言語がすべて異なる**ため、コード流用は物理的にも起きにくい。言語差による性能比較の交絡は PROJECT_SPEC §7.2 の方法で緩和する。

## 4. 完成品の評価基準
全案共通（ACCEPTANCE_CRITERIA）に加え、独自機能は次の追加テストで評価する。

| 案 | 追加テスト |
|---|---|
| A | 同一入力の`--verify`再実行で一致、改ざん（ルール/結果）を検出、`lint`が危険ルールを指摘、Hostヘッダ偽装/トークン無しのHTTPアクセスを拒否 |
| B | 模擬改修M1〜M3の変更量、DSL式の表現力テスト（シナリオR-S1〜S12の充足）、一括検査と比較結果の正しさ |
| C | 100万行でのRSS・時間・CPU使用率、並列数を変えても結果が完全一致、メモリ上限指定時の挙動 |
| D | プロファイラの型推定精度、**ルール提案の誤提案率**（提案を全承認して実行したときの誤検出が0）、標準タスクの操作ステップ数 |
