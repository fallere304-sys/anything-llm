# ARCHITECTURE_D.md — D案「独創性・UX」（Python ＋ PySide6）

## 1. コンセプト
「**プロファイル先行**」。従来は利用者が先にルールを決めて検査するが、D案は先にデータを**自動プロファイリング**し、データの実態から**ルール案を自動提案**する。利用者は提案を「承認／却下」するだけで検査でき、結果は「問題の一覧」ではなく「次にやること」（修正レシピ、仮想修正プレビュー）として提示する。

## 2. 設計思想
- **3ステップのウィザード**: ①ファイルを選ぶ ②「データの特徴」と「提案ルール」を確認して承認 ③結果を見て直す。専門用語を避ける。
- **推測は必ず承認制**: 提案ルールは自動適用しない。各提案に**根拠（例: 「この列は98%が日付形式 yyyy-MM-dd」）と確信度**を表示。承認されたルールのみが検査に使われる。
- **誤提案を設計で抑える**: 確信度が閾値未満の提案は出さない／「必須」は欠損率が低いときのみ提案、など保守的に。
- 検査コアはGUI非依存（`csvqc_core`）。ProfilerとRuleProposerは独立モジュール。
- 修正は**一切書き込まない**: 「仮想修正プレビュー」は画面上の差分表示のみ（元データは不変、保存機能なし）。

## 3. 技術選定（固定）
| 用途 | 採用 |
|---|---|
| 言語 | Python 3.12（CI）。コンテナの3.13でも動作確認 |
| GUI | PySide6 6.7.x（Qt Widgets、QAbstractTableModelで大量行を遅延表示）。ライセンスはLGPL-3.0（動的リンク配布、ライセンス表示を同梱）|
| 文字コード | 標準`codecs`（`cp932`, `utf-8`） |
| Excel | openpyxl 3.1.x（書き込みのみ、write_onlyモード） |
| 正規表現 | 標準`re`（バックトラック型 → INTERFACE_SPEC §3.4の静的チェック必須。さらに値長4096超は形式不一致扱い） |
| 履歴 | 標準`sqlite3` |
| テスト | pytest、pytest-qt（offscreen） |
| 配布 | PyInstaller 6.x の onedir → ZIP（Windows CI）。onefile不採用（AV誤検知リスク） |

## 5. 要点
- **Profiler**（ストリーミング1パス＋サンプリング）: 列ごとに 欠損率、型の推定（integer/decimal/date(書式分布)/string）、桁数/最大長、値の種類数、数値のmin/max、「一意らしさ」。**100万行でも1パスで完了**（メモリは列ごとの小さな集計器）。
- **RuleProposer**: Profile → `ProposedRule[]`（ルール断片＋根拠＋確信度＋却下しやすい説明文）。提案の種類: 型・日付書式・必須・最大長・範囲(外れ値除く)・重複キー候補・許可値(種類数が少ない列)。ルールJSON(INTERFACE_SPEC v1)として出力可能（保存・再利用）。
- **正しさの担保**: 「提案を全承認して同じファイルを検査すると**誤検出0**」であること（提案はそのデータに適合する範囲で作る＝自己整合性）を自動テストにする。逆に、意図的な異常を含むデータで提案が異常を取り込んでしまわないよう、**外れ値・少数派の形式は提案に含めず「注意」として表示**。
- **結果画面**: 種類別カード → セルを色分けしたテーブル → 選択行に「何が・なぜ・どう直すか」と修正レシピ（例: 全角数字→半角の候補値）。**修正候補はOPT-08（決定的に導けるもののみ）**。

## 6. メリット / デメリット / リスク
- メリット: 非IT利用者の負担が最小、独自性が高い、Qtでネイティブな大量行表示、コンテナでoffscreen検証の可能性。
- デメリット: 配布サイズ大(~150MB)、PyInstallerのAV誤検知、LGPLの扱い、Pythonゆえ速度は低い。
- リスク: **提案の誤り**（利用者が承認ミスをする/偏ったデータから誤ルールを学ぶ）、PySide6の`offscreen`がコンテナで動くか未検証、日本語フォント/IME。
- 緩和: 承認制＋根拠表示＋保守的閾値、自己整合性テスト、コアとGUIの分離。

## 7. 独自機能（D-14〜D-16）
プロファイラ(D-14)／ルール提案(D-15)／修正レシピ＋仮想修正プレビュー(D-16)／ウィザードUI(D-11)。

## 8. 検証計画
