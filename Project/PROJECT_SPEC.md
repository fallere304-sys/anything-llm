## 1. 目的

業務CSVの欠損・形式不正・重複・値矛盾・異常値を自動検出し、非IT利用者にも分かる形で報告するWindows向けローカルデスクトップアプリを作る。**検出と報告に徹し、元CSVは絶対に変更しない。自動修復は行わない。** [確定]

最終目標は「4つの異なる設計思想の独立実装を、同一テストデータ・同一基準で競わせ、最良案をベースに他案の長所を統合する」こと。[確定]

## 4. 実現可能性評価

### 4.1 そのまま実現可能
CSV解析（UTF-8/BOM/CP932、引用符・埋込改行）、欠損/重複/型/範囲/日付/空白/列数/ヘッダ重複の検出、ルールJSON保存、CSV/Excel/HTML出力、ストリーミングによる100万行処理、ポータブル配布（フォルダZIP形式）。

### 4.2 要件の再定義が必要（原理的に完全実現不可能 → 代替案）

| # | 要求 | 問題 | 代替・再定義 |
|---|---|---|---|
| F-1 | 文字化けの検出 | 文字化けの完全判定は原理的に不可能（バイト列としては正当な文字列になり得る） | 「**疑い**検出」に再定義。U+FFFD混入、典型的mojibakeパターン（例: UTF-8をCP932で誤読した際に出る文字列）、デコード確信度の低下、で判定。確信度付きで報告 |
| F-2 | 不自然な文字列 | 定義が主観的で、ルール化できない | 判定基準を分解し**個別にON/OFF可能**にする: 制御文字、ゼロ幅文字、私用領域文字、異体字/機種依存文字、全角半角混在、連続同一文字の過多、等。具体仕様は REQUIREMENTS FR-CHK-09 |
| F-3 | 項目間の論理矛盾 | 任意の矛盾は自動発見できない | **宣言的ルールで表現できる矛盾**に限定（日付前後関係、条件付き必須、条件付き範囲、列間の等値/大小、合計一致）。任意コード実行は**安全性のため禁止**。矛盾の自動発見は将来のAI拡張（O-09） |
| F-4 | 異常値の検出 | 範囲指定は決定的だが、統計的外れ値は誤検出を生む | 範囲外=決定的な「エラー」。統計的外れ値(IQR等)は**別カテゴリ「注意(warning)」**で既定OFF。誤検出と検出漏れのトレードオフを利用者が制御できる |
| F-5 | 誤検出ゼロかつ検出漏れゼロ | ヒューリスティックなルールではprecisionとrecallは両立不可 | **決定的ルールは両方100%**を合格基準。**ヒューリスティックなルールは別基準**（ACCEPTANCE_CRITERIA §3）で、severityを分離 |
| F-6 | 文字コード自動判別 | 短いファイルではShift-JIS/UTF-8の判別が確定できない | 自動判別＋確信度表示＋**手動指定**。Shift_JISは拡張を含む**CP932として解釈**（①㈱髙﨑等） |
| F-7 | 修正候補の提示 | typo訂正等は推測になる | 決定的に導ける候補のみ（前後空白除去、全角数字→半角、日付の正規形、列の統一形式）。推測的候補は提示しない／信頼度を付す。**書き込みは一切しない** |
| F-8 | 別のWindows PCで確実に動作 | 実機差（WebView2有無、VC++ランタイム、AV/SmartScreen）を全て網羅できない | 依存を同梱/静的リンクし、検証対象を **Windows 10 22H2 / 11（ユーザー実機）＋CIのWindows Server相当**と明示。[CIのwindows-latestはServer系でありWin10/11デスクトップそのものではない: 合理的推定] |
| F-9 | 無償のみ＋EXE署名 | コードサイニング証明書は有料 | **未署名**で配布。SmartScreen警告・AV誤検知の可能性を文書化し、SHA-256を併記。フォルダ形式ZIPを優先（単一ファイル自己展開型はAV誤検知が増える傾向 [合理的推定]） |

### 4.3 要求間の矛盾・緊張関係

| # | 緊張 | 解決方針 |
|---|---|---|
| T-1 | 「4案を独立」 vs 「共通テストデータで機械比較」 | **共有してよいのは仕様・データ・テストのみ（実装コードは共有しない）**。全案が同一の「ヘッドレス実行契約」（§7）を実装する。共通資産は `/Project/eval/` に置き、どの案のコードにも依存しない |
| T-2 | 優先順位8位の速度 vs C案が性能特化 | 総合評価の重みで調整（§8）。C案は低優先軸での優位を「用途別優位性」として報告する |
| T-3 | 「データの安全性」2位 vs 履歴に問題値を既定保存(D-03) | ユーザー決定を尊重し、**緩和策を必須化**（§6: 履歴全削除、保存OFF設定、初回告知、ログに値を出さない、保存先の明示） |
| T-4 | AI分析の将来拡張 vs 外部送信禁止 | 拡張点（Analyzer interface）は**ローカル実行のみ**。ネットワーク呼び出しを既定で禁止する設計 |
| T-5 | 「検査ルールの保存・再利用(必須)」 vs 「テンプレート保存(希望)」の重複 | 必須=ルールJSONの保存/読込。希望=名前付きテンプレートの管理（一覧・複製・同梱プリセット） |
| T-6 | ポータブル性 vs 履歴・設定の保存場所 | 既定は**EXEと同階層の `data/`**。書込不可の場所では `%LOCALAPPDATA%` へフォールバックし、利用者に明示。レジストリは使用しない |
| T-7 | 4案×希望機能9個の工数 vs ユーザーの手作業(プロンプト中継)負担 | タスクを「1案あたり約8〜12本」に抑制（PHASE 3で調整）。希望機能は§REQUIREMENTSのTier制で案ごとに重点を変える |

## 5. 完成の定義（概要。詳細は ACCEPTANCE_CRITERIA.md）

各案の「完成」= 以下をすべて満たすこと。1つでも欠けた案は完成扱いしない。

1. GitHub Actions(windows-latest)で自動ビルドされ、ポータブルZIPが成果物として生成される
2. ヘッドレス実行契約に準拠し、共通ゴールデンコーパスでの機械評価が実施できる
3. 必須要件(MUST)を全て満たす
4. 元CSVが変更されない（SHA-256一致テストが合格）
5. ユーザーのWindows PCでのGUIスモークテスト（チェックリスト）に合格

## 6. セキュリティ・データ保護 基本方針 [確定+設計方針]

- 元CSVは**読み取り専用で開く**。出力先が入力ファイルと同一パスなら拒否する。
- ネットワーク通信を行わない（外部送信なし）。テレメトリ・自動更新なし。
- **ログには実データ値を出力しない**（件数・ID・行番号のみ）。
- 履歴DBには問題値を保存する(D-03)。必須の緩和策: ①保存先パスを設定画面に常時表示 ②「履歴を全て削除」機能 ③「問題値を履歴に保存」設定のON/OFF（既定ON） ④初回起動時に保存内容と場所を告知 ⑤DBに対し外部送信・同期機能を持たせない。
- レポート出力: CSV/Excelは**CSVインジェクション対策**（`=`,`+`,`-`,`@`,タブ,CRで始まるセルの無害化）、HTMLは**全値をエスケープ**。
- ユーザー定義の正規表現・ルールは**サイズ上限と線形時間エンジン（または実行時間制限）でReDoS対策**。ルールファイルは宣言的JSONのみで、**コード実行(eval等)を禁止**。

## 7. 客観評価を可能にする構造（プロジェクトの核）

### 7.1 ヘッドレス実行契約（全案必須・詳細は PHASE 3 の INTERFACE_SPEC.md）
```
<app>.exe --headless --input <csv> [--rules <rules.json>] [--encoding auto|utf-8|cp932]
          --output <findings.json> [--report-dir <dir>]
終了コード: 0=検査完了(異常有無問わず) / 2=入力エラー / 3=ルール不正 / 4=内部エラー
```
`findings.json`（共通スキーマ v1）は少なくとも次を含む: `schema_version`, `file{path,sha256,encoding,encoding_confidence}`, `stats{records_total,records_checked,findings_total}`, `findings[{rule_id, record_no, line_no, column, value, severity, message, suggestion}]`。

### 7.2 正解データ（ゴールデンコーパス）
- 正常な合成CSVに**既知の不正を決定的に注入**して生成する（乱数シード固定）。正解`expected.json`は注入結果から機械的に得るため、正解自体に誤りが入らない。
- 加えて手作りエッジケース（CP932、引用符内改行、BOM、空ファイル、巨大セル等）と、実務模擬データ（医療・介護風の**架空**データ）を用意。
- 評価スクリプト（`/Project/eval/`、Python）が precision / recall / F1 をルール別・総合で算出。マッチングキーは `(rule_id, record_no, column)`。
- 言語差による性能測定の交絡を避けるため、**速度・メモリはヘッドレス実行のEnd-to-End（プロセス全体）を同一マシン（CI runner）で測定**し、言語差があることをレポートに注記する。

### 7.3 共通資産の責任分担
共通評価基盤（コーパス生成器・採点器・CI workflow）も**GPT-OSS-120Bに実装させる**（タスクID `E-xxx`）。Claude Codeは仕様・プロンプト作成と検品・実行確認のみを担う。実装寄与率は案(A〜D)と共通基盤(E)を分けて集計する。
（v0.1では「Claudeが実装する」と誤記していた。v0.2で訂正。役割定義は §12）

## 8. 評価の重み（案・要ユーザー確認）

「完成の定義」を満たさない案は順位付け対象外（ゲート）。通過した案を以下で採点。

| 評価項目 | 配点 | 主な測定 |
|---|---:|---|
| 検査精度 | 25 | コーパスでのprecision/recall（決定的ルールは100%基準） |
| データの安全性 | 20 | 元ファイル不変、CSVインジェクション/HTML注入/ReDoS/外部通信ゼロのテスト、ログ漏洩検査 |
| 安定性 | 15 | 異常入力コーパス（fuzz含む）でのクラッシュ数、100万行完走、キャンセル動作 |
| ルールの柔軟性 | 12 | 必須ルール型の網羅、複合ルール表現、ルール保存/再利用、スキーマ検証 |
| 操作性 | 10 | 標準タスクの操作ステップ数（計測）＋ユーザー実機評価（**主観**と明示） |
| 保守性 | 8 | テストカバレッジ、静的解析、モジュール結合度、ビルド再現性 |
| 拡張性 | 6 | 「新ルール追加」「新出力形式追加」を行う模擬改修での変更ファイル数・行数 |
| 処理速度 | 4 | 100万行E2E時間・ピークRSS |
| **合計** | **100** | 独創性は採点せず、PHASE 7 の統合候補選定で別途考慮 |

## 11. 4コンセプトの方向性（予告。PHASE 2で確定）

## 12. 役割分担（v0.2で明確化）

| 担当 | 役割 |
|---|---|
| **Claude Code** | 要件分析、設計、**GPT-OSSが最も成果を出せる粒度への処理分割**、**GPT-OSS向けプロンプトの作成**、インターフェース仕様の確定、成果物の検品（ビルド・テスト実行・コードレビュー）、修正指示プロンプトの作成、評価・統合の判断 |

| **ユーザー** | プロンプトをGPT-OSSへ入力し、成果物をClaudeへ渡す。Windows実機でのGUI確認 |

Claudeが直接コードを書くのは例外のみ（GPT-OSSが繰り返し失敗した場合等）。その際は理由と範囲を DELIVERY_LOG に記録する。Claudeが書くのは「プロンプトと仕様書」が中心で、コードの確認は検品として実行・テストする。
