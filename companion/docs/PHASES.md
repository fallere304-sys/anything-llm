## Phase 3: 記憶 — 完了(2026-10-02)

### 実装
- 種類の分離: 短期記憶(会話履歴)/ 長期記憶 / プロジェクト記憶 / 作業履歴 / 重要事項(どの記憶にも付けられる「重要」フラグ)
- メタデータ: 作成日時・更新日時・情報源(ユーザー入力 / 会話から / AIの提案)・情報源の参照・信頼度・種類・関連プロジェクト・状態
- `MemoryService`(Memory Tool の実体)
  - ユーザー操作(保存・更新・削除・承認・却下)は即時反映し、作業履歴に記録
  - AI の入口は `propose()` のみ。提案は「承認待ち」で保存され、承認されるまで文脈に入らない
- 文脈への取り込み: 重要事項 → 現プロジェクトの記憶 → 関連度(2文字単位の一致) → 新しさ の順で、文字数予算(`BUDDY_MAX_MEMORY_CHARS`)内に詰める。他プロジェクトの記憶は入れない。「古い可能性がある、矛盾時は確認せよ」と注記
- プロジェクト: 作成・名前変更・削除(記憶が残っていれば削除を拒否)。会話をプロジェクトに紐付け
- 作業履歴: 追記専用。LLM呼び出し(所要時間・成否)と記憶の変更を、行為者(AI / ユーザー)付きで記録
- UI: 🧠 記憶パネル(記憶 / 承認待ち[件数バッジ] / 作業履歴 / プロジェクト)、上部の PJ 選択、各発言の「＋覚える」
- 可視化: 「記憶」「PJ」ノードが実際の参照時に光る。参照件数を処理ログに表示

### テスト
- pytest 70件成功(検証ルール、承認前は文脈に入らないこと、取り込み順・予算・プロジェクト範囲、チャットへの注入、作業履歴、API、認証)
- ヘッドレスChromium(390px): PJ作成 → 記憶追加 → PJ付き会話で送信 → 疑似LLMのシステムプロンプトに記憶が入ったことを確認 → 発言から「覚える」 → AI提案の承認 → 作業履歴表示。コンソールエラー無し

### 問題点・未検証
- AI から記憶を提案する経路は未接続(Phase 4 のツール呼び出しで `propose()` を接続する)
- 関連度は文字の一致で、意味の近さは測れない(例: 「飲み物」と「コーヒー」は結びつかない)。記憶が数百件を超えたら埋め込み検索を検討
- 記憶は最大 2000 文字/件。全件を毎回走査するため、数千件規模では見直しが必要
- 更新履歴(変更前の内容)は保持しない。作業履歴には操作の事実のみ残る
- 作業履歴は自動では削除されない(肥大化対策は未実装)
